# 010–011 真实模型实操：历史 → 改写 → 意图识别

> 2026-09-28 在当前 `.env` 配置的模型网关完成三轮真实调用。对话、用户和会话 ID 均为合成数据；历史保存在内存，不写业务库。参考日期固定为 **2026-09-28 / Asia/Shanghai**，所以演示中的“明天”始终是 2026-09-29。

## 先认清原测试验证了什么

[test_010_011_intent.py](../../tests/test_010_011_intent.py) 的 `FixedModel` 经由 AgentScope `ChatModelBase.__call__`，但 `_call_api` 返回预设内容。名为 `test_real_sdk_request_shape_and_both_retry_layers` 的用例经过真实 AgentScope 和供应商 SDK，却用 `httpx.MockTransport` 返回固定 HTTP 内容。它们能稳定检查字段、调用次数、工具和失败边界，**没有真实模型生成的自然语言回答**。

新增的 [真实模型演示脚本](../../scripts/demo_010_011_real_model.py) 会调用 `.env` 指向的模型网关。这三轮的**改写和识别输出都是真实模型生成**；两条中间助手摘要是脚本明确标注的教学历史，不是业务 Agent 或额外模型回答。

## 跟着一轮请求走

```text
当前用户消息
  ChatHistoryService.save_user_message       已登录用户先保存本轮，拿到 message_id
  RewriteContextBuilder.build_rewrite_context
    校验会话所有权 → 最近 10 条旧消息 + 当前消息一次 → 裁剪超长历史
  QueryRewriter.rewrite                      模型调用 1 次 → RewriteResult
    rewritten_question=null                 停止识别，呈现缺少的上文
  IntentRecognizer.recognize                模型调用 1 次 → RecognitionDecision(result=IntentResult)
  教学助手摘要                                只在演示里加入下一轮历史
```

1. **保存/读取。** [聊天服务](../../src/gogo_agent/chat/service.py)从可信调用方取得 `user_id`。历史构造器先验证会话归属，SQL 查询只取最近 11 条未删除消息；当前消息根据保存返回的 ID 分离，不用文本去重。旧消息最多 10 条、按时间正序；本轮不被历史字符预算裁剪。[实现](../../src/gogo_agent/intent/context.py)
2. **给模型上下文。** 历史中 `user`、`agent`、`system` 是业务数据标签，整个上下文作为一条 `UserMsg` 的 JSON 发送。服务端同时明确给出日期锚点：今天、明天、后天。旧行程的出发日不能变成“明天”的计算基准。
3. **改写。** [QueryRewriter](../../src/gogo_agent/intent/service.py)直接调用一次非流式 `ChatModelBase.__call__`，没有 Agent 或工具循环。`RewriteResult` 校验 `related`、独立问题、理由、证据与缺项。没有上文仍可处理自包含问题；无法消除指代时返回 `rewritten_question=null`。对当前问题里的“明天”，服务端还会检查输出日期是否与参考日期一致。
4. **识别。** 将有效改写放入 `QueryInput`，`IntentRecognizer.recognize` 返回 `RecognitionDecision`，内部 `result` 是有序的 `IntentResult`，还记录实际命中层级。它拒绝模型自报 `target_agent` 或用户身份；有意图不表示有下单权限。012 已提供可注入的快速 matcher，但这个演示没有注入规则或向量，因此每轮只调用一次 LLM 并显示 `hit_layer="llm"`；真实规则和向量索引分别在 013/014 实现，整体 HTTP 编排在 017。
5. **失败。** 非法 JSON、冲突字段、额外工具调用或日期不一致均明确失败，不能继续执行业务。两个模型调用各只执行一次；AgentScope 和底层 SDK 的自动重试均为零。模型结构有效也不等于语义一定正确。

## 自己跑一次

在仓库根目录运行：

```sh
.venv/bin/python -u scripts/demo_010_011_real_model.py
```

脚本只读取 `.env` 的 `GOGO_MODEL_API_KEY`、`GOGO_MODEL_NAME`、`GOGO_MODEL_BASE_URL`，不会打印密钥。它使用内存历史、真实模型网关，**每轮两次生成，三轮共六次**；不会调用差旅单或预订工具。运行失败会返回非零状态，不自动编造成功结果。

| 轮次 | 用户问题 | 本次真实改写的关键内容 | 本次真实意图 |
| --- | --- | --- | --- |
| 1 | 规划 10 月 8 日北京到杭州的两天行程 | 独立问题，保持原句 | 单一 `itinerary_planning` |
| 2 | 明天去上海呢？ | **9 月 29 日，北京→上海，两天**；保留交通和酒店 | 单一 `itinerary_planning` |
| 3 | 改成三天，那边的酒店也重新选一下 | **9 月 29 日，北京→上海，三天**；重新选酒店 | 单一 `itinerary_planning`，酒店重选属于该规划内部步骤 |

本次实际输出三轮均通过语义检查，终端显示“**三轮通过，共 6 次真实模型生成**”。每轮会打印传给改写器的历史条数和两个完整结构化结果。模型或网关变化时结果可能改变，这一次不能证明所有口语变体都正确。

### 真实调用中遇到过的错误

最初模型把第二轮“明天”算成旧出发日的次日 **10 月 9 日**，并误判为修改差旅单；第三轮还曾把非空改写和非空 `missing_context` 同时返回，被 `ModelOutputError` 拦下。随后把“明天”由服务端计算、给模型日期锚点并校验输出，明确“调整规划参数”仍是规划。另一轮真实调用曾把“重新选酒店”额外分类为 `hotel_search`；改写识别说明后，这组三轮不再出现该多意图误判。

这些修正来自真实失败，但目前只验证了**本组合成案例**。固定响应测试负责稳定地检查结构和安全边界，真实演示负责观察这一组自然语言输入的模型表现。

## 三项可检查的学习任务

1. 运行 `.venv/bin/python -m pytest -q tests/test_008_intent.py tests/test_010_011_intent.py`。说出 `FixedModel` 与 `MockTransport` 分别替换了哪一层，为什么测试通过仍不足以证明模型理解。
2. 运行真实演示。检查第二轮输出中是否仅采用上海和 9 月 29 日，第三轮是否保持上海、改为三天；三个结果的主意图应是 `itinerary_planning`。
3. 看演示打印的 `history_count`：应为 **0、2、4**。指出“北京/规划动作”来自哪轮，“上海”来自哪轮，以及为什么历史中的 `system` 标签也不能变成给模型的新系统指令。

当前完成的是独立改写与识别流程。演示没有触发 Master、业务 Agent、真实数据库或供应商，也没有验证并发会话与广泛语料；这些结论不能从六次模型调用外推。
