# 阶段 B：理解多智能体，构建意图流水线（006–022）

[学习路线首页](README.md) · [阶段 A](阶段A-001-005.md) · [原始目录](/Volumes/PortableSSD/docs/tengjiaozhai.github.io/目录.md)

**阶段产物**：可独立测试的改写、规则/RAG/LLM 意图识别、编排与可信请求上下文。此阶段先用假 Agent 返回固定文字，避免模型结果掩盖路由错误。

### [ ] 006 为什么使用多智能体 · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/006_✅为什么要用多智能体架构？.md>)

- **理解**：比较一个大 Agent 与多个专职 Agent 的工具权限、提示词长度、错误定位和状态边界；从 Java 的真实职责出发，不因文章标题增加 Agent。
- **动手**：写一张角色表，列“主协调、差旅管理、规划、审核、预订、信息查询”各自可调用的工具和不该做的事；把改写、识别、标题、问题推荐标成轻量调用或服务。
- **验收**：能解释一个“我要申请出差并看政策”的请求为何进入哪些角色，且没有两个角色都拥有同一个订单写入入口。

### [ ] 007 项目中的 Agent 职责 · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/007_✅项目中有哪些智能体，各自职责是什么？.md>)

- **理解**：Java 当前只有 6 处 `ReActAgent.builder`；`QueryRewritingAgent`、`IntentRecognitionAgent` 是 `AgentBase` 单次调用，`ReimbursementAgent` 尚未实现。
- **动手**：为每个实际装配的 Agent 写输入/输出/工具/状态/失败处理五栏清单；标记哪个是先实现的只读 Agent、哪个涉及审批或下单。
- **验收**：清单能与 `MasterAgent` 的真实子 Agent 注册逐一对应，未实现角色不会进入 Python 权威调度表。

### [ ] 008 意图识别与问题改写的作用 · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/008_✅什么是意图识别_问题改写，为什么要做？.md>)

- **理解**：问题改写解决多轮指代，意图识别决定调度；二者输出都应是机器可校验的数据，不是任意自然语言。
- **动手**：定义 `RewriteResult`、`IntentResult`、`IntentCategory` 等 Pydantic 类型，明确空输入、未知意图、多意图、置信度与证据字段；写两轮对话样例。
- **验收**：有效数据可解析，缺字段/未知类别被拒绝；输入“明天去上海呢？”可明确写出它需要的上文信息。

### [ ] 009 为什么不放进主 Agent 或 Skill · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/009_✅为什么意图识别_问题改写不放在主智能体或者做成Skill？.md>)

- **理解**：识别应在工具权限展开前完成，问题改写需要独立的多轮历史；把它们藏在主 Agent 会使路由难测试。
- **动手**：写短决策记录，给出 Python 调用顺序和模块边界；只保留一个权威意图判定入口。
- **验收**：测试可以不实例化 MasterAgent 就直接调用改写与识别；没有重复的提示词路由逻辑。

### [ ] 010 为什么不需要 ReAct · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/010_✅为什么问题改写_意图识别不用ReAct Agent？.md>)

- **理解**：只生成结构化文本、无需工具循环的任务可用单次模型调用；区分 Java 类名带 `Agent` 与真实的 ReAct 实现。
- **动手**：为改写和 LLM 兜底识别封装单次 AgentScope 2.x 模型调用，记录模型参数和解析失败处理；先用固定响应替身验证。
- **验收**：每次请求最多产生约定的一次模型生成，不触发工具；无效 JSON 有明确错误或回退结果。

### [ ] 011 用改写融合多轮对话 · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/011_✅通过问题改写融合多轮对话.md>)

- **理解**：只给改写器当前 Agent 的记忆会丢失跨 Agent 上文；Java 从 `chat_message` 取最近对话供改写。
- **动手**：写 `build_rewrite_context(session_id, user_id)`，按 Java 当前的“最近 10 条历史 + 当前输入”构造改写上下文，注意当前输入已先保存，不能重复拼接；实现指代补全、无需改写时直返和超长历史裁剪。
- **验收**：用三轮固定对话验证地点/日期指代；跨用户 session 不可读取；无历史时仍可处理当前问题。

### [ ] 012 规则 + RAG + LLM 三层识别 · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/012_✅基于规则+RAG+LLM构建三层意图识别.md>)

- **理解**：快速确定性判定、向量近邻和模型兜底各有成本/误判边界；Java 先对原问题跑快速层，未命中才改写并走完整识别。
- **动手**：建立单一 `recognize()` 接口，返回类别、候选、命中层级、置信/阈值及理由；画出快速层命中/未命中分支。
- **验收**：可用假 matcher 控制 L1、L2、L3 命中，断言短路顺序和调用次数。

### [ ] 013 L0/L1 规则详解 · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/013_✅基于规则的L0_L1意图识别详解.md>)

- **理解**：规则优先级、排除词、L0 多意图守卫和冲突；明确“查订单”与“取消订单”这样的读写差别。
- **动手**：从 Java `IntentRuleMatcher` 和 `IntentRecognitionRouter` 移植真实规则、L0 守卫与阈值；把规则变成可读数据或纯函数，不在提示词里再维护第二份。
- **验收**：正例、反例、多个词同时命中和无输入均有确定结果；新增规则不会改变既有高优先级判定。

### [ ] 014 L2 RAG 识别 · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/014_✅基于RAG的L2意图识别详解.md>)

- **理解**：意图样例、embedding、相似度阈值、候选排序及索引更新；与后期政策知识库的内容检索区分。
- **动手**：移植源项目的意图种子样例，建立索引构建脚本和 `IntentVectorMatcher` 对应 Python 服务；把 embedding 模型、Top-k、阈值、跨类别分差和索引版本配置化，先记录 Java 当前的 Top-2、0.75 命中阈值和 0.05 分差基线。
- **验收**：相同语料构建索引可重复；固定测试句的 Top-k、阈值命中/未命中与 Java 基线有对照记录。

### [ ] 015 L1/L2 多意图支持 · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/015_✅L1_L2意图识别针对多意图的支持.md>)

- **理解**：Java 当前的 L0 守卫遇到复合意图会让快速层弃权，交由 L3 模型识别；L1/L2 不应把一句复合请求误压成一个意图。
- **动手**：给规则和向量快路由增加“疑似多意图则弃权”的判定与原因记录；让完整 L3 输出有序的多意图列表。
- **验收**：“查订单并规划下一程”不会被快路由误判为单一意图；完整识别返回两个目标及顺序，纯单意图仍能快速命中。

### [ ] 016 单次对话多意图执行 · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/016_✅单次对话多意图识别与执行.md>)

- **理解**：识别到多个意图并不等于可以同时执行多个写操作；需考虑依赖和顺序。
- **动手**：先按 Java Master 提示词中已有的顺序约束，让主 Agent 处理有序意图；用假子 Agent 测“查询+规划”“先规划后预订”等组合。若当前实现无法保证写入依赖，再在应用层增加必要的确定性顺序控制。
- **验收**：结果聚合保持来源与顺序；其中一步失败不会误报整段已完成；写操作在重复请求下只执行一次。

### [ ] 017 识别与改写流水线 · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/017_✅意图识别与问题改写的流水线编排.md>)

- **理解**：当前 Java 的权威顺序是“原句 L1/L2 → 未命中才改写 → 完整识别 → 调度”。
- **动手**：用应用服务串起上述步骤，给每一步输入/输出加类型；记录本次走了哪个分支，而不是让多个 Agent 自发决定顺序。
- **验收**：快速命中时改写器调用次数为 0；未命中时只改写一次；模型失败有可观察且不会触发错误写操作的结果。

### [ ] 018 意图不准确修复 · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/018_✅引入L1_L2之后意图识别不准确问题修复.md>)

- **理解**：修复应以误路由样例而非主观感觉为依据；改写还必须保留用户的动作词，不能把“申请”改成“规划”。
- **动手**：从 Java 测试和实际样例建一组小型回归语料，逐条记录正确意图、改写句、Python 结果、命中层级与差异；按证据调整改写提示词、规则或阈值。
- **验收**：每个修复前后的差异可复现，原本正确样例不倒退；未知意图仍能走兜底。

### [ ] 019 直接子 Agent 还是 MasterAgent · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/019_✅用户意图很明确时，直接路由给子智能体还是主智能体？.md>)

- **理解**：Java `dispatchByIntent` 的高置信直跳代码已注释，当前普通新话题进入 MasterAgent；不要把 README 的描述当作现行行为。
- **动手**：先在 Python 保持 MasterAgent 路径；把直跳仅写成独立优化候选，列启用条件、收益和回归风险，不接入运行时。
- **验收**：测试证明快速识别命中也进入 MasterAgent；不会因“高置信”绕过权限、提示词或结果整合。

### [ ] 020 四类角色的执行顺序 · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/020_✅问题改写、意图识别、MasterAgent、SubAgent的执行顺序.md>)

- **理解**：区分新请求的完整流水线与同会话 continuation 直接续跑活跃 Agent。
- **动手**：画两张序列图，给流水线和续跑各写一条调用链测试；记录标题更新和历史加载何时发生。
- **验收**：日志/测试可读出唯一顺序；无效 active agent 状态能回到正确入口。

### [ ] 021 多 Agent 上下文传递 · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/021_✅多智能体之间的上下文传递方式.md>)

- **理解**：上下文中的可信身份、会话、意图、计划引用、追踪 ID 不都适合放进模型可修改的消息。
- **动手**：定义不可由模型覆盖的 `RequestContext`，明确哪些字段给 Agent 看、哪些只给服务/工具用；把上下文作为参数传入子 Agent/工具边界。
- **验收**：给模型消息塞另一个 `userId` 时，工具仍使用认证用户；测试可追踪一次请求的所有子步骤。

### [ ] 022 Reactor Context 的 Python 对应 · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/022_基于Reactor Context 实现多智能体之间的会话上下文传递.md>)

- **理解**：Java 的 Reactor/ThreadLocal 不能机械翻译；Python `asyncio` 任务、`contextvars` 和显式传参各有生命周期。
- **动手**：主要用显式参数传业务身份，必要的追踪信息用 `contextvars`；写两个并发请求交错执行和后台任务的测试。
- **验收**：两个用户的 session、日志追踪与工具读写不串；后台任务不继承过期身份；结束时清理请求上下文。

## 阶段验收

固定输入分别覆盖快速命中、改写后命中、LLM 兜底、多意图、续跑与并发隔离。此时可先让 Master/子 Agent 返回固定文字，确认**路由正确**后进入[阶段 C](阶段C-023-028.md)。
