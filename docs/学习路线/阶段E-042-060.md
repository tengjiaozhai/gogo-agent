**阶段产物**：可追踪的行程计划、确定性方案计算、受控旅行信息查询、独立审核结果与外部凭证边界。所有供应商写操作仍用模拟服务。

### [ ] 042 为什么规划使用 Plan-and-Execute · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/042_✅为什么行程规划智能体要用Plan-and-Exucute？.md>)

- **理解**：规划涉及收集条件、并行找候选、组合、审核和可能重做；单次模型回答无法可靠表示步骤状态。
- **动手**：定义计划步骤、输入/输出、完成/失败/待确认状态和终止条件；对照 Java 已使用的 `PlanNotebook`，评估 AgentScope 2.x 的计划能力如何承接并推送进度。
- **验收**：中途搜索失败和用户改日期时，能指出从哪一步重新执行，已确认的订单写操作不会重复。

### [ ] 043 行程规划智能体 · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/043_✅行程规划智能体的功能介绍及开发.md>)

- **理解**：看 Java `ItineraryPlanAgent` 的工具、提示词和结果存储；区分“提出候选方案”与“执行预订”。
- **动手**：构建 Python 规划 Agent，先接模拟搜索和确定性方案工具；把规划状态存到会话关联的计划记录，返回可引用的 `plan_id`。
- **验收**：输入城市、日期、预算能得到有来源的方案；参数不足时请求补充；没有确认时不下单。

### [ ] 044 为什么方案设计做成工具 · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/044_✅为什么行程方案设计不用Skill要用工具？.md>)

- **理解**：交通/酒店的价格、时间和政策计算可确定，模型适合解释权衡，不适合暗算评分。
- **动手**：把组合/排序函数放在普通 Python 业务模块，再用 `FunctionTool` 或锁定版本等价 API 暴露；写选择依据短记录。
- **验收**：直接调用业务函数与 Agent 经工具调用得到相同评分；提示词变化不改变计算结果。

### [ ] 045 行程方案设计工具细节 · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/045_✅行程方案设计工具设计细节.md>)

- **理解**：追 Java 规划工具的去程、住宿、返程组合、时间价格归一化、政策软约束和偏好评分。
- **动手**：用固定机票/酒店候选集逐项移植过滤、组合、评分与代表方案选择；核对当前 Java 权重 `0.20/0.10/0.40/0.30`，不抄旧文章的早期权重；每项中间值可打印或测试。
- **验收**：相同候选输入下，Python 与 Java 的入选/淘汰原因和排序可对照；空候选、异常价格、跨时区航班有明确结果。

### [ ] 046 目的地实时联网查询 · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/046_✅出差目的地实时联网查询工具定义及开发.md>)

- **理解**：实时天气/新闻等数据有来源、抓取时间和有效期；失败不能变成模型编造的确定事实。
- **动手**：对 `DestinationLiveTools` 建 Python 客户端与返回 schema；设置超时、可用性错误和来源时间字段。
- **验收**：模拟正常、超时、无结果三种响应；最终回答能区分查到的数据和未验证的信息。

### [ ] 047 天气 MCP 接入 · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/047_✅天气查询工具_MCP的接入.md>)

- **理解**：MCP 客户端有连接/关闭生命周期、工具发现和参数 schema；它与普通 HTTP API 工具同属外部能力但协议不同。
- **动手**：按锁定版本的 AgentScope 2.x 官方 MCP 文档接入现有天气服务；先连测试服务，记录工具列表和错误转换。保留短期免费天气查询与超范围时转向 MCP 长期预报的边界。
- **验收**：可以列出并调用天气工具，断连/超时有可复现结果；不向 MCP 服务发送不必要的用户隐私。

### [ ] 048 旅行 Skill/MCP 对比 · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/048_✅市面上可用的旅行相关skill_mcp工具对比.md>)

- **理解**：一个供应商可能提供 Skill、MCP、CLI 等多个入口，重复接入会导致能力和凭证双轨。
- **动手**：核查源项目当前实际启用的途牛、航班管家、Rolling Go、天气及签证能力，建立“用途、入口、只读/写入、凭证、是否注册到当前 Agent、保留与否”清单。现行规划/预订 Agent 的 SkillBox 注册了途牛；航班管家和 Rolling Go 的资源存在不等于已启用。
- **验收**：每个行为只有一个计划中的权威调用入口；未启用的旧 Skill 不被误迁移。

### [ ] 049 途牛 Skill · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/049_✅途牛 Skill介绍及接入.md>)

- **理解**：阅读现有 tuniu CLI 的输入、结构化结果、错误码与凭证注入方式，识别搜索与下单的不同风险。
- **动手**：先做搜索客户端/适配器和模拟 CLI 响应，不运行真实下单；隔离执行目录和参数，保留供应商原始请求 ID。
- **验收**：固定搜索样例得到规范化候选；命令失败、非 JSON、超时均能返回错误且不把密钥写入日志。

### [ ] 050 航班管家 Skill · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/050_✅航班管家Skill介绍及接入.md>)

- **理解**：`flight-manager` Skill 与 `FlightApiKeyHook` 存在，但当前规划/预订 Agent 未注册该 Skill，相关 Key 管理方法也已注释。
- **动手**：做一份调用契约和用假数据完成的独立小练习，验证航班号、时间、舱位、价格转换及 Key 占位符替换；不接入正式规划路径，除非后续确认启用。
- **验收**：练习使用假 Key 且模型上下文没有明文；迁移清单清楚标“当前未启用”，不把它算作已迁移业务功能。

### [ ] 051 Rolling Go Skill · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/051_✅Rolling Go Skill介绍及接入.md>)

- **理解**：Rolling Go Skill 资源存在但当前规划/预订 Agent 未注册；通用 Shell 工具和 `rgh` Hook 仍可能参与运行，需用调用证据确认。Java 的 `rgh` Shell 包装和 Token 同步路径值得学习，多用户隔离是核心要求。
- **动手**：用假 CLI 做按用户/会话分配工作空间与凭证引用的小练习，验证登录/退出与跨节点 Token 同步；不接入正式酒店搜索路径，除非后续确认启用。
- **验收**：两用户并发练习不共享 Token 或文件；过期登录态要求重新授权；迁移报告标明此 Skill 当前未注册。

### [ ] 052 为什么审核使用子 Agent · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/052_✅为什么行程审核不用Skill要用子智能体？.md>)

- **理解**：原文章讨论独立审核 Agent，但当前 `ItineraryReviewAgent` 已标 `@Deprecated`；权威路径是规划 Agent 调 `ItineraryReviewTools.review_itinerary`。
- **动手**：写一页“文章方案与现行路径”对照，明确 Python 先迁移审核工具及其内部评估流程，不另外装配一个独立 ReAct 审核 Agent。
- **验收**：审核仍能独立给出结论，但系统里只有一条权威审核入口，且无供应商下单权限。

### [ ] 053 行程审核智能体 · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/053_✅行程审核智能体的功能介绍及开发.md>)

- **理解**：当前 `review_itinerary` 工具内运行六维确定性客观检查、三个主观评估和仲裁；原文的“独立审核 Agent”是旧架构。
- **动手**：先写客观规则引擎，再做三个有限的评估调用和仲裁器，统一输出 `ReviewResult` schema；每条问题含维度、严重程度、证据和建议。
- **验收**：硬规则失败必定触发整改；主观评估异常可见且不掩盖硬否决；完整计划通过，冲突计划指出具体字段。

### [ ] 054 最终审核工具 · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/054_✅行程方案最终审核工具定义及开发.md>)

- **理解**：最终校验是模型意见之外的硬规则检查，应防止遗漏关键数据。
- **动手**：让审核工具按认证用户、出发地、目的地和日期从计划存储读取结果，不让模型传完整 JSON；将确定性与主观结果合并成最终结构化结论。
- **验收**：空方案、超预算、日期冲突、不匹配出发地会被拦住；工具失败不能被模型口头“审核通过”覆盖。

### [ ] 055 第三方鉴权总览 · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/055_✅Agent中如何实现第三方鉴权？.md>)

- **理解**：区分服务级 API Key、用户级 OAuth Token、CLI 环境变量和 MCP 凭证；每一种的归属、更新与过期不同。
- **动手**：画“用户→服务→供应商”的授权图，为每个实际集成记录凭证持有者、可访问资源和撤销方式。
- **验收**：能回答某次供应商请求使用谁的授权；无法授权时不会用其他用户或管理员的密钥兜底。

### [ ] 056 直接 Token 配置 · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/056_✅基于Token 直接配置方式做鉴权.md>)

- **理解**：配置型 Token 只适合与实际服务契约相符的场景，不能写进提示词、源码或持久化日志。
- **动手**：实现服务端安全读取与请求头注入；只在发往目标供应商时使用，错误中屏蔽 Token。
- **验收**：缺 Token 请求不发出；单元测试能验证头部已注入但日志/异常中没有明文。

### [ ] 057 OAuth PKCE 与本地回调 · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/057_✅基于OAuth PKCE + 本地回调做鉴权.md>)

- **理解**：PKCE 的 `state`、`code_verifier`、授权码交换与过期刷新；先核对源项目是否对相应平台实际使用。
- **动手**：先用模拟授权方做一个独立 PKCE 小练习，验证 `state` 和 verifier；再读现行 `rgh` CLI 的 OAuth 包装：Java 应用交给 CLI 处理 PKCE，本身负责用户隔离、授权链接返回和 Token 捕获。Python 主流程先用模拟 CLI 验证此边界；只有确需接管时才实现应用内回调与换令牌。
- **验收**：正常登录可恢复原用户会话；错误 `state`、过期 code、重复回调和跨用户 Token 均失败。

### [ ] 058 外部 Skill 的生产可用性 · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/058_✅改造外部Skill使其具备生产环境可用性.md>)

- **理解**：外部 CLI/Skill 的退出码、超时、标准输出格式、工作目录和资源占用都可能失控。
- **动手**：给保留的每个 Skill 加输入限制、超时、错误映射、输出解析、用户隔离和清理；不将任意 shell 文本直接拼进命令。
- **验收**：模拟长时间挂起、非法 JSON、巨大输出和进程退出失败，Python 服务均能返回可定位错误且不泄露凭证。

### [ ] 059 API Key 动态管理、加密和脱敏 · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/059_✅如何实现API KEY的动态管理与加密、脱敏.md>)

- **理解**：对照 Java `ApiKeyService`、`SecretCipher`、`SensitiveMasker`；区分加密存储与展示脱敏。
- **动手**：实现用户级凭证增删查、加密与密钥轮换预案；核对 Java 的 API Key 与 Rolling Go Token 使用不同加密实现，Python 选择受审计的现代加密方案，不机械复制旧算法。在 API、日志、工具响应和模型上下文中只暴露最小必要信息。
- **验收**：数据库里无明文 Key；用户只能管理自己的 Key；更新/撤销后旧 Key 不再被调用；负例日志检查无明文。

### [ ] 060 ReviewAgent 获取 PlanAgent 结果 · [原文](</Volumes/PortableSSD/docs/tengjiaozhai.github.io/thoughts/060_✅ReviewAgent如何获取到PlanAgent的规划结果？.md>)

- **理解**：长计划可通过 `plan_id`/计划存储传递，不需要把整份结构反复塞进提示词。
- **动手**：建立计划读写仓储和所有权校验；当前审核工具按用户和行程读取共享结果，Python 可用稳定 `plan_id`/版本表达同一归属，并记录审核使用的版本号。
- **验收**：同一版本计划可重复审核；计划修改后旧审核不能误标为新计划通过；跨用户 `plan_id` 访问失败。
