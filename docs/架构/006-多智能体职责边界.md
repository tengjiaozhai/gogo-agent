# 006 多智能体职责与工具边界

> 本文是阶段 B 的 006 架构产物。Java 对照目录是 `/Users/shenmingjie/workSpace/LLMentor-teach/gogo-agent`，下文 Java 文件定位均相对其中的 `src/main/java/com/gogo/travel/`，提示词相对 `src/main/resources/`。结论来自静态源码；模型选路与工具调用尚未运行验证。Python 目前只有 005 的 `GoGo` 单 Agent 文本对话；本文不表示这些业务 Agent 已接入 Python。

## 为什么按职责拆分

| 比较点 | 一个 Agent 承担全部职责 | 按实际职责拆分后的边界 |
| --- | --- | --- |
| 工具权限 | 查询政策时也能看到申请、审批、下单等写入工具，误调用的后果大。 | 信息查询只拿只读工具；差旅单写入和供应商下单分别交给对应角色。工具入口仍须在服务端校验身份、状态和参数。 |
| 提示词与上下文 | 查询、规划、审核和下单的指令及历史一起增长，冲突和无关信息更难定位。 | 各角色只接收完成当前任务所需的指令与上下文；跨角色传递会话、意图和结果引用。 |
| 错误定位 | 很难判断失败来自意图判断、规划、审核还是订单写入。 | 改写/识别由流水线负责，业务 Agent 只处理自己的结果，业务服务返回明确的失败原因。 |
| 状态边界 | 一份状态同时承载多种任务，恢复时难判断谁拥有未完成动作。 | 对话历史、AgentState、计划结果、差旅单和供应商订单各有明确归属；续跑时恢复对应角色的状态。 |

拆分依据是**需要不同工具权限、任务状态或独立检查**，而不是类名中是否含有 `Agent`。单次改写、意图识别、标题更新和问题推荐没有工具循环需求，保留为轻量模型调用或确定性服务，不为了数量增加业务 Agent。角色划分也不代替服务端的鉴权与订单幂等约束。

## 当前调用链与角色表

Java 普通新请求的静态路径是 `ChatController → ChatAgentExecutor → AgentPipelineService → 快速识别/条件改写/完整识别 → MasterAgent → 已注册子 Agent`；续聊可能直接恢复活跃 Agent。快速识别命中后直跳子 Agent 的代码未启用，普通新请求仍交给 Master。证据：`controller/ChatController.java:54-95`、`agent/service/ChatAgentExecutor.java:132-145`、`agent/service/AgentPipelineService.java:134-156,206-224`。Python 当前的 [ChatAgentExecutor](../../src/gogo_agent/chat/executor.py) 直接构造一个 `GoGo` Agent，还没有上述路由和子 Agent。

下表把 **Java 实际注册的能力** 和 **Python 目标职责边界** 分开；Java 注册了工具不代表每次请求都会调用。差旅申请的审批单与管理员审批决定属于不同操作；行程方案审核也不是管理员审批。

| 角色及当前装配 | Java 实际可调用能力 | Python 目标禁区 |
| --- | --- | --- |
| 主协调 `MasterAgent`：普通新请求的协调入口 | `ask_user`；`itinerary_manage_agent`、`itinerary_plan_agent`、`info_agent`、`booking_agent` 四个子 Agent 入口。`agent/MasterAgent.java:79-126` | 只委派、提问和整合结果；不直接持有差旅单、供应商订单或管理员审批写工具；不从模型输出中接受可信 `userId`。 |
| 差旅管理 `ItineraryManageAgent` | `TravelOrderWriteTools`（申请提交、修改、取消、审批状态查询）、差旅单/预订读取、冲突检查、用户信息读写。`agent/ItineraryManageAgent.java:24-56` | 不创建供应商机票/酒店订单；不作管理员审批决定；不代替规划 Agent 产出或审核方案。 |
| 规划 `ItineraryPlanAgent` | 政策、差旅单/预订读取、用户信息读写、API Key、搜索与规划、方案读取/审核/HTML、目的地及天气/签证能力；另外注册了带 `tuniu` 命令且启用 `.withWrite()` 的 shell skill。`agent/ItineraryPlanAgent.java:64-79,125-134` | 规划工具只负责候选与方案；供应商下单应仅由预订角色执行，不作管理员审批决定，也不创建差旅申请。**Java 当前 shell 权限尚未落实这个禁区。** |
| 审核职责：当前由 `ItineraryReviewTools.review_itinerary` 承担 | 读取已有方案并输出客观校验与模型评估报告，由规划 Agent 调用；独立 `ItineraryReviewAgent` 已弃用，未注册到 Master。`agent/ItineraryPlanAgent.java:76`、`agent/ItineraryReviewAgent.java:33-45` | 不修改差旅单审批状态，不触发供应商下单，不把方案报告当作管理员审批。 |
| 预订 `BookingAgent` | 差旅单/预订/方案读取，`BookingWriteTools.cancel_booking`、用户信息与 API Key、`tuniu-cli` 下单；结果由 `BookingPersistenceHook` 持久化。`agent/BookingAgent.java:59-103,108-116` | 不创建或提交差旅申请，不作审批决定；订单写入须有服务端确认、审批和幂等约束，不能只靠提示词。 |
| 信息查询 `InfoAgent` | 政策、目的地实时信息、天气/签证 MCP，景点/差旅政策/指南知识库；没有差旅单或预订写工具。`agent/InfoAgent.java:30-77` | 不创建/修改差旅单、规划结果或供应商订单，不作审批决定。 |

Java 规划 Agent 的提示词要求规划阶段只用搜索能力，但实际 `tuniu` shell 带写权限；其可调用面与 Booking 的供应商下单面重叠。006 的 Python 职责表将供应商订单写入收敛给 Booking；到 061–065 实际注册工具时必须消除该重叠，之后才能声称运行时实现了唯一写入入口。现有 Booking 提示词中的“先确认、先查审批”也需要由业务工具校验，不能仅凭角色指令当作权限门禁。

`ReimbursementAgent.build()` 当前返回 `null`，Master 也未注册报销子 Agent；报销不加入本次角色表或 Python 权威调度。证据：`agent/ReimbursementAgent.java:19-24`、`agent/MasterAgent.java:83-126`。

**不放进 Agent 的业务能力：**认证与会话归属由 HTTP 依赖和服务端会话服务负责；差旅单事务、审批状态转移、订单去重、供应商结果持久化由相应业务服务/工具负责。管理员审批只经具备管理员身份的独立接口进入，不交给聊天 Agent 自行决定。[002 静态契约](../契约样例/002-用户旅程静态契约.md)列出了这些入口与数据副作用。

**轻量步骤：**Java 的 `QueryRewritingAgent`、`IntentRecognitionAgent` 继承 `AgentBase`，使用单次模型调用；规则与向量识别由识别路由处理。`ConversationTitleService` 使用一次快速模型调用生成标题，`QuestionRecommendationService` 在最终回复后用一次快速模型调用生成推荐问题。它们不是 Master 的业务子 Agent，也不获得差旅单或预订写入工具。证据：`agent/QueryRewritingAgent.java:24-30,50-71`、`agent/IntentRecognitionAgent.java:27-47,68-119`、`business/chat/service/ConversationTitleService.java:41-43,57-78`、`agent/service/QuestionRecommendationService.java:33-77`。Python 005 的标题由会话服务取首条消息生成；是否移植 Java 的模型标题在后续编号处理。

## 复合请求走向与写入归属

以“**我要申请出差并看政策**”为例，目标路由是服务端先认证并校验会话归属，识别层保留“申请”和“看政策”两个目标，Master 分别交给差旅管理与信息查询。`InfoAgent` 读政策；`ItineraryManageAgent` 收集地点、日期、事由，缺字段时先询问，具备执行条件后才由差旅管理业务工具创建/提交差旅单。这个请求不需要规划、方案审核或预订，更不应生成供应商订单。具体的多意图守卫与识别顺序由 012–017 实现。

**当前 Java 的可见差异：**这句原文里的单字“并”不在 L0 强连接词或子句切分规则中，政策规则也不匹配单独的“政策”；`申请出差` 会命中差旅申请规则。静态推演是 L1 返回单个 `travel_application`，快路径跳过改写并交给 Master，不能证明 InfoAgent 一定被调用。证据：`agent/intent/IntentRuleMatcher.java:69-78,130-132,195-198,239-265`、`agent/service/AgentPipelineService.java:139-149`。006 记录目标和差距，不在本步提前修改 013/015 的识别规则。

| 写入对象 | Python 目标中的唯一负责入口 | 其他角色的关系 |
| --- | --- | --- |
| 差旅单及本地申请 | 差旅管理的 `TravelOrderWriteTools` → 差旅单业务服务 | Master 仅协调，信息查询只读；审批决定仍由管理员接口处理。 |
| 规划结果与方案文档 | 规划 Agent 的规划/保存工具 | 审核读取方案并返回报告；不创建差旅单或供应商订单。 |
| 供应商订单及其本地记录 | `BookingAgent` 的供应商调用与预订结果持久化路径 | 差旅管理、规划和信息查询都不注册同一供应商写入入口；Java 规划 shell 的权限差异见上文。 |
| 管理员审批决定 | 管理员 HTTP 接口 → 审批业务服务 | 所有聊天 Agent 均不能直接作出决定。 |

006 的验收边界是能据此解释角色选择和唯一订单写入归属。输入/输出/工具/状态/失败的逐 Agent 清单在 007 完成；Python 多 Agent 注册与真实路由尚属后续编号。
