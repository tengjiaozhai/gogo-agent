# 0001 记忆条目的状态由位置决定，不设状态字段

## 背景

自动记忆需要对旧条目做三种处理：被新事实取代、被细化后保留、因上限被挤出。常见做法是给每个条目加 `status` 字段（active / superseded / archived），或者维护一份独立的 JSON 状态表。

本项目的外部存储是 ReMe 的纯文本记忆文件：一次 `/save` 覆盖整个文件，检索按目录前缀返回全文。在这个约束下，状态字段和状态表都要额外读写一次，并且要和记忆文件本身保持一致——两处写入在并发下会出现一方成功、一方失败。

## 决定

状态不写进条目字段。用**文件位置**表达状态：有效条目在 `digest/users/<hash>/auto-memory.md`，退役条目在 `history/users/<hash>/auto-memory-history.md`。历史目录不在检索前缀下，因此退役条目自动不参与召回。

条目内只保留两类元数据：身份标识（内容哈希，创建后不变）与来源标识（本轮请求 ID）。退役原因写在历史文件的注释里。

## 后果

- 同一次 `/save` 同时完成"内容更新"和"状态变更"，不存在两处写入不一致的窗口。
- 召回不需要过滤状态，读取即得到当前有效集合。
- 代价：无法表达"某条目对某些查询失效、对其他查询仍有效"这类细粒度状态。当前需求不需要，若将来需要，应在引入图数据库时一并解决，而不是在文本文件里加字段。
- 代价：历史文件随运行时间增长且无上限。可接受，因为它不参与检索，只在人工排查时读取。

## 替代方案

- **条目内加 `status` 字段**：需要每次读取后过滤，且退役操作仍需改写主文件，收益是能保留细粒度状态。当前需求不要求。
- **独立 JSON 状态表**：与记忆文件双写，并发下需要额外的锁与校验，是已知容易出错的形态。
- **每条目一个文件**：位置天然表达状态，但召回时要多次读取，且 ReMe 的按前缀检索退化为逐文件读取。
