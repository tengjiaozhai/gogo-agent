### 1.1 本编号用到的 Python 语法与对象生命周期

- **`async def` / `await`**：`review()` 与工具函数是协程。`asyncio.gather(...)` 并行等待三个主观评估器，结果顺序与输入顺序一致。它只相似于 Java 的 `CompletableFuture.allOf`，但取消、异常传播与 Reactor 不同。
- **`async with asyncio.timeout(...)`**：超时上下文，进入时开始计时，超时抛出 `TimeoutError`。它不是 try-with-resources；没有需要关闭的资源。
- **`Protocol`**：`SubjectiveAssessor` 只描述形状，不需要 `implements`。`StaticAssessor` 能被传入，仅因它有 `source` 属性和 `assess` 方法。
- **`@dataclass(frozen=True)`**：`Itinerary`、`Leg` 创建后字段不可修改，接近 Java 的不可变 `record`。
- **`model_copy(update=...)`**：浅拷贝并替换字段，类似 Java 的 clone-with-builder。服务用它生成新状态，不修改旧对象；`steps.py` 用 `model_copy(deep=True)` 避免共享列表。
- **闭包**：`make_service()` 中的 `ids = count(1)` 被 `id_factory` lambda 捕获，每次调用递增，这就是 `demo-001` 能稳定复现的原因。它和 Java 中的实例字段不同，外部无法直接访问 `ids`。
- **`StrEnum`**：`PlanStepName`、`ReviewVerdict` 的值是字符串，JSON 序列化后保持文本。
- **Java `PlanNotebook` 的 Python 对应**：已检查 AgentScope 2.0.8 的 site-packages，没有可直接对应的计划模块。因此进度由 `planning/steps.py` 的可序列化状态承接，并随 `PlanView` 一起保存；这是本项目的实现，不是 AgentScope 提供的能力。
- **只相似不等价**：`round2()` 复刻 Java `Math.round` 的“半数向上”，结果一致；但 Java 的时间解析会去掉 `Z` 并忽略时区偏移，Python 按真实时刻计算，跨时区航班的通勤时长会不同（见第 5 节）。

## 3. 练习：先预测，再运行核对

每题先写下答案，再运行对应命令。

**E1（042）**：计划连续三次搜索失败后，`next_step` 是什么？`terminated` 是什么？
- 答案：`search_candidates`，`True`。第三次失败后不再自动重试；`next_step` 仍指向搜索，是为了告诉调用方从哪里重做。
- 验证：`--case 042` 的第三行。

**E2（045）**：“时间最短”为什么选 `F1|H2|F4`，而不是 `F1|H2|F3`？
- 答案：去程都是 F1（130 分钟），返程 F3 与 F4 都是 130 分钟，总通勤并列 260 分钟。平局先看总价：F3 版本为 1200 + 1100 + 840 = 3140 元，F4 版本为 1200 + 700 + 640 = 2540 元。同理酒店也按总价在 H1、H2 之间选择 H2。最终 `F1|H2|F4` 胜出。
- 验证：在 B8 处查看 `raw_fastest.combo_id`，或运行 `--case 045` 后比较 `时间最短` 的通勤与价格。

**E3（045）**：“价格最低”的 `T1|H2|T2` 为什么仍然保留，并带有体验标记？
- 答案：它是最便宜的组合（1573 元），但去程通勤 5 小时 30 分、返程 4 小时 30 分，都属于长通勤。15% 容差内没有无风险的替代组合，因此保留最便宜方案，并把风险写进 `experience_flags`。
- 验证：`--case 045` 第二段的 `体验标记`。

**E4（054）**：候选只保留酒店 H1，同一代表方案的审核结论是什么？
- 答案：`pass`。H1 的 420 元不超过 450 元上限，星级 4 不超过 4 星，代表方案 `F1|H1|F4` 总价 2740 元未超 5000 元阈值，出发地与目的地与审批单一致。
- 验证：`review_plan(plan, proposal_tag="综合最佳", ...)`，或在 B10 查看三个评估结果。

**E5（054）**：把体验评估器替换为抛异常的替身，结论如何？
- 答案：`warning`，且 `needs_rework=False`。异常以 `available=False` 出现在结论里，不会被当作通过，也不会把客观结论改为失败。
- 验证：`--case 054` 第二行。

**E6（060）**：同一内容上重复审核，前一次审核是否仍然有效？调用 `compute` 之后呢？
- 答案：重复审核后仍有效，因为审核只绑定内容版本，保存版本会增加但内容版本不变。`compute` 会改变内容版本，之前的审核失效。
- 验证：`--case 060` 中的“同一内容重复审核”与“重新计算后”两行。

**E7（045，改代码实验）**：让 `out_leg.arrival` 晚于 `in_leg.departure`，会得到什么？
- 答案：B6 命中，这些组合进入 `excluded`，原因“返程出发不晚于去程到达”；只有全部组合都被过滤时才抛出 `ALL_FILTERED`。
- 验证：把 F1 的到达时间改为 `2026-10-22T23:00:00+08:00` 后，结果为组合数 18、被淘汰 9（已在本仓库运行核对）。全部过滤的情形见 `tests/test_042_060_planning.py::test_045_empty_and_abnormal_inputs_have_explicit_results`。

| 客观规则 | 由 Agent 描述 | `ObjectiveReviewEngine` 六维确定性检查 | `objective_review()` 六维确定性检查 |
| 主观评估 | 同一 Agent 内完成 | 三个有限的评估调用 | 三个 `ModelSubjectiveAssessor`，每个一次调用，共用稳定模型角色（`planning/assessors.py`） |
| 仲裁 | 由模型给出 | 仲裁器 | `arbitrate()`，确定性规则 |
| 写权限 | 无 | 无供应商下单权限 | 无；审核只写审核结论字段 |

**结论**：Python 不另外装配独立审核 Agent。审核能力在函数与服务内，入口只有一条（规划 Agent 工具 `review_plan`），这符合 052 验收“系统里只有一条权威审核入口，且无供应商下单权限”。

## 5. 覆盖范围与未验证项

**已覆盖（有自动测试或脚本）**

- 步骤推进、失败次数、终止、条件变化后的重做（042）。
- 客观组合、过滤、归一化、综合分与代表方案选择，包括红眼规避、跨时区时长、空候选、异常价格（044、045）。
- 工具 schema 不含 `user_id`，且不含下单或取消工具；计划可从工具完整走到审核（043）。
- 客观硬规则、主观异常、仲裁、缺少审批单（053、054）。
- 版本、审核绑定、跨用户访问失败（060）。

测试文件：[tests/test_042_060_planning.py](../../tests/test_042_060_planning.py)，共 22 项，本指南编写时通过。

**与 Java 不一致（有意）**

1. 超过政策酒店上限、审批阈值或用户预算，Python 判 `fail`；Java 的预算校验判 `warning`。原因：054 验收要求“超预算会被拦住”。
2. 价格为 0 或负数的候选、到达早于出发的候选被明确剔除并记录原因；Java 未显式剔除。
3. 时长按真实时刻计算，跨时区航班结果与 Java 的墙上时间不同。
4. 审核入口用 `plan_id` 定位计划，不接受模型传出发地、目的地、日期。
5. 计划没有“每日活动”，因此到达缓冲与返程缓冲检查未移植。
6. 新增提前预订天数检查（Java 已有，此处保留）。

**未验证或未接入**

- **真实搜索**：046–049 由其他模块处理，本指南只用 `simulated_search`。
- **真实模型**：053 的评估器在测试中使用脚本化替身，真实稳定模型的回复质量与 JSON 遵从性未验证。模型输出不合法时该维度记为不可用，结论至多为 `warning`，不会静默通过。
- **043 真实途牛路径**：本机没有安装 `tuniu-cli`，也没有用户 Key。要运行真实搜索，需要三样东西：(1) 本机安装 `tuniu-cli` 并设置 `GOGO_TUNIU_CLI` 指向它；(2) 设置 `GOGO_SECRET_KEYS`，并建好 `user_api_key` 表；(3) **Python 侧目前没有让用户录入途牛 Key 的入口**（`ApiKeyService.save` 存在，但没有 HTTP 路由），因此在此之前所有用户都会得到“未配置”。
- **043 聊天端到端**：路由与工具装配有测试，但没有用脚本化主模型跑完一轮完整对话；真实模型对规划工具的选择未验证。前端触发链路（练习库、聊天页、Scalar、断点位置与已知 503 现象）见[前端触发规划 Agent 逐步调试](阶段E-前端触发规划Agent逐步调试.md)。
- **043 计划存储**：计划只保存在进程内存中，重启丢失，多实例不共享；`itinerary_plan` 表未进入 MySQL 迁移。
- **043 预算**：候选搜索不按预算过滤，预算只在审核的用户预算检查中生效。
- **数据库**：`itinerary_plan` 表只在内存 SQLite 中创建，未加入 MySQL 迁移脚本，生产库中不存在。
- **订单关联**：`order_id` 字段保留，但没有任何路径会写入它。
- **Java 对照**：没有运行 Java 基线的同一批候选做逐条比较，结论来自静态移植与手工推演。
