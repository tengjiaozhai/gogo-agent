# 018：确认提交与方案选择的动作、对象和工具边界

## 修复的实际问题

2026-10-23 的会话原句是“确认提交”。改写补入历史酒店明细后得到“确认提交综合最佳方案（北京⇄上海……酒店H2两晚……）”，旧 L1 命中 `hotel_search`，主 GoGo 的工具列表为空，所以回答没有管理子 Agent 可调用。

现在裸确认与泛指方案选择先承接历史；明确动作由能解释该动作的规则判定。背景交通/住宿明细不抢占申请或选择，但“酒店价格多少”等独立问题继续参与多意图判断。原始错误改写会弃权，不能继续高置信命中酒店；如果改写仍没有补全对象，明确报 `ModelOutputError`，没有修复重试或另一套兜底分类。

“选择综合最佳方案”仍是选择行程方案，不能被改写成申请、提交或预订；否定约束“不要/不必/请勿提交”仍是否定。没有历史时直接返回 `needs_context`，不调用模型或向量服务；历史存在但对象仍不明确时，改写应返回 `rewritten_question=null` 与具体 `missing_context`。


它先预置一轮“规划并准备提交差旅申请”的业务历史（不调用模型），然后发送三次“确认提交”。这是全部隐藏准备：没有先建差旅单，也没有提前签发确认令牌。

稳定输出：

```text
第1轮：travel_application → GoGo → ItineraryManageAgent；差旅单数量=0
第2轮：travel_application → GoGo → ItineraryManageAgent；差旅单数量=1
第3轮：travel_application → GoGo → ItineraryManageAgent；差旅单数量=1
```

每轮固定一次改写、两次主模型和两次管理模型调用；真实 L1 识别独立问题，不调用 L2 或 L3。每次运行的消息、trace、reply、差旅单 ID 和确认令牌会变化，不应按字面值比对。首次只生成申请摘要；下一轮带前次工具签发的令牌提交；重复提交由现有幂等机制返回同一单。退出脚本时隔离 SQLite 消失。

真实模型实跑发现，仅要求先取令牌不足以保证等待用户：模型可能在同一轮内取令牌后立即再调用提交工具。现在令牌 v2 绑定可信 `session_id` 和签发时的 `request_id`，同会话的后续用户轮次才能提交；同轮再次调用返回 `CONFIRMATION_REQUIRED`，不会创建申请。旧版令牌显式返回 `CONFIRMATION_INVALID` 并要求重新获取摘要；没有双格式兼容或数据表迁移。正常确认重放仍由同一申请摘要的幂等键保证不重复创建。

## 显式委派重试与失败摘要

另一个真实问题是：管理 Agent 第一次超时后，GoGo 重试并成功生成摘要，但旧代码只要看到任何一次 `failed` 就拒绝整轮保存。页面已有摘要，管理 AgentState 却没有保存令牌，所以下一轮确认仍从空令牌开始。真实重试还改写了 `question`，不能靠文本相似度证明它与上一次是同一任务。

现在每次委派有服务端 `attempt_id`，首次调用建立 `task_id`。失败结果返回 `retry_of`；GoGo 若决定重试，只传这个编号、让 `question` 留空。`DelegationAttempts.run` 校验编号属于本轮同一工具的失败调用，然后复用保存在内存中的原始问题。未知编号、其他轮次/工具编号、已成功调用的编号，以及同时填写新问题的重试均拒绝，不执行子 Agent。编号不具备用户授权能力，管理工具仍从原 `RequestContext` 获取身份并校验确认令牌。

执行器按每条显式重试链的最终结果决定能否保存，保留每次 `failed`/`completed` 记录，不删除失败历史。不同任务即使调用相同子 Agent，成功也不能覆盖原任务失败。主 Agent 中断或达到最大轮次仍失败。没有新增自动重试循环，也没有调整工具的幂等与两段式确认。这个编号协议是 Python 本次实现；未核实 Java 是否存在同等契约。

回复和状态由 `chat/repository.py:reply_transaction` 一起提交：SQL 共用同一 Session/事务，内存仓储失败时恢复快照。主/子状态或活跃路由保存失败时，已写入的助手消息也回滚，刷新不会把失败摘要重新显示成成功回复。该事务仅覆盖聊天记录和运行状态，不回滚此前已执行的业务工具；例如业务提交后聊天保存失败，应先查询差旅单结果，重复提交仍依赖现有幂等，不把超时解释为未创建订单。
