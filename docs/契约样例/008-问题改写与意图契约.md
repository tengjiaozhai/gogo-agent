# 008 问题改写与意图数据契约

> 已完成：类型定义、固定样例与结构校验。日期：2026-09-27。实现入口是 [intent/models.py](../../src/gogo_agent/intent/models.py)，[JSON 样例](008-两轮对话.json)同时供本文和针对性测试使用。样例是人工写定的期望数据，没有调用模型、识别规则、数据库或业务工具。

## 1. 这一步分别解决什么

- **问题改写**补全跨轮指代和省略，保留用户正在要求的动作。例如调整“规划”的目的地，仍然是规划需求，不能改成下单。
- **意图识别**把诉求归入明确类别，并给出有序事项、主要意图、置信等级和依据。识别到类别不等于已授权执行，也不证明业务能力已实现。
- **数据校验**让调用方明确区分有效结果、未完成改写和非法输出。它只验证数据结构与字段关系，不能证明模型的语义理解、证据真实性或日期推理正确。

008 提供可独立使用的数据模型。[010–011](010-011-单次调用与上下文.md) 已使用它们实现独立模型调用与业务历史上下文。当前 `ChatRequest`、HTTP 对话执行器和 `GoGo` Agent 尚未接入这些模块，不能据此声称聊天 API 已开始拒绝空问题或支持多意图路由；完整编排由 012–017 推进。

## 2. 模型与字段

下表四个 008 模型的字段均为必填，包含应显式提供的空列表和 `null`；全部模型拒绝未定义字段。文本去除首尾空白后不能为空，内部空格保持原样。所有模型和字段都有中文说明，可通过 `model_json_schema()` 读取。011 新增的 `HistoryMessage` 与 `RewriteContext` 及其默认字段见 [上下文说明](010-011-单次调用与上下文.md)。

| 模型 | 字段 | 含义与约束 |
| --- | --- | --- |
| `QueryInput` | `question` | 本轮非空用户问题；身份、会话归属和历史由调用方提供，不由本模型声明。 |
| `RewriteResult` | `related` | 严格布尔值，表示与**已提供**历史的相关性。无可关联历史时为 `false`；它不表示“改写是否成功”。 |
| `RewriteResult` | `rewritten_question` | 完成后为非空独立问题；无需改写时可保留原句；缺必要上下文时为 `null`。 |
| `RewriteResult` | `reason`、`evidence`、`missing_context` | 非空理由；至少一个非空依据片段；缺失上下文清单。结果为 `null` 当且仅当缺失清单非空。 |
| `IntentItem` | `intent`、`confidence` | 类别枚举；置信度仅接受 `high`、`medium`、`low`，不是概率或检索相似度。 |
| `IntentItem` | `reason`、`evidence` | 非空分类理由和至少一个非空依据片段。依据可注明本轮、上轮或服务端日期来源，但不能当作身份或写入授权。 |
| `IntentResult` | `intents` | 至少一项，保持输入的事项顺序；模型不自动排序或去重。 |
| `IntentResult` | `primary_intent` | 必须是 `intents` 中出现的类别，可以不在第一项。 |
| `IntentResult` | `multi_intent`、`overall_reason` | 严格布尔值且等于 `len(intents) > 1`；整轮判断和排序理由不能为空。 |

**空输入与未知意图区别：**空字符串、纯空白、`null` 或数字不是有效 `QueryInput`。`unknown` 是一个合法类别，表示有问题文本但无法明确分类；`flight_query` 等未定义或拼错的类别触发 `ValidationError`，不会被自动改成 `unknown`。

**改写缺上下文与业务缺参数区别：**不知道“那个”指什么、当前要申请还是规划，会阻止形成独立问题；明确说“帮我申请出差”则已足以识别申请意图，具体地点、日期等表单缺项交给后续业务流程处理。

### 十六类意图的准确代码

| 意图范围 | 枚举传输值 |
| --- | --- |
| 差旅单与审批查询 | `travel_application`、`travel_cancel`、`travel_modify`、`approval_query`、`travel_order_query` |
| 规划与候选搜索 | `itinerary_planning`、`flight_search`、`train_search`、`hotel_search` |
| 预订相关 | `booking` |
| 报销 | `reimbursement`（仅可表示诉求，对应业务尚未实现） |
| 信息查询 | `policy_query`、`attractions_query`、`general_info` |
| 问候与未知 | `greeting`、`unknown` |

本模块没有 Agent 注册或类别到执行工具的映射。`target_agent`、`user_id` 等自由输入字段会被拒绝；后续应用层从可信上下文和实际装配决定执行角色。来源层级与向量分数不由模型自报；[012 的外层识别结果](012-三层识别与短路.md)已承载实际尝试的来源与候选，真实向量分数留待 014 的 matcher 提供。

## 3. 两轮对话与上下文要求

固定的服务端参考日期为 **2026-09-27，Asia/Shanghai**。样例不读取运行当天日期。

| 轮次 | 用户输入 | 期望改写 / 意图 |
| --- | --- | --- |
| 第一轮 | 帮我规划2026年9月30日从北京去杭州的两天出差行程，包括往返交通和酒店。 | 保留原句，`related=false`；`itinerary_planning`。交通和酒店属于该规划任务的范围。 |
| 助手上下文 | 当前需求是9月30日从北京去杭州，出差两天，规划往返交通和酒店。 | 是固定示例中的历史消息，不表示系统已经完成规划。 |
| 第二轮 | 明天去上海呢？ | 请规划2026年9月28日从北京去上海的两天出差行程，包括往返交通和酒店。`related=true`；仍为 `itinerary_planning`。 |

第二轮必须知道：

1. 上一轮的**任务动作是规划**，不能仅凭“去上海”推断为差旅申请、查询或预订。
2. **出发地北京、时长两天、往返交通和酒店**继续沿用。
3. 本轮的**上海**替换杭州，**明天**替换原出发日；相对日期要用给定参考日期与时区解释，不能依赖模型猜测当前日期。

同一句追问在没有历史时，`missing_history` 样例的 `rewritten_question=null`，并明确列出任务动作、出发城市、时长/返程要求三个缺项。008 没有实现自动追问或继续调度，消费者必须先处理这个未完成结果。

同一 JSON 文件还提供：

- `multiple_intents`：政策查询排第一，差旅申请为第二项和主要意图，验证事项顺序与主要意图不必相同。
- `unknown_intent`：直接对模糊原句识别时返回显式 `unknown`；与其中未完成的改写结果各自独立，不表示流水线会把未完成改写继续送入业务执行。

可以从仓库根目录用当前虚拟环境交互解析样例：

```python
import json
from pathlib import Path
from gogo_agent.intent import QueryInput, RewriteResult, IntentResult

data = json.loads(Path("docs/契约样例/008-两轮对话.json").read_text(encoding="utf-8"))
turn = data["dialogue"][1]
query = QueryInput.model_validate(turn["query"])
rewrite = RewriteResult.model_validate(turn["expected_rewrite"])
intent = IntentResult.model_validate(turn["expected_intent"])
print(rewrite.rewritten_question)
print(intent.model_dump_json())
```

## 4. 与 Java 基线的对应及收敛

Java 对照目录为 `/Users/shenmingjie/workSpace/LLMentor-teach/gogo-agent`。类路径相对 `src/main/java/com/gogo/travel/`，提示词相对 `src/main/resources/`。

- `IntentCategory` 的 16 个 code 与 `agent/intent/IntentCategory.java:14-44` 对齐。置信度沿用 `agent/intent/IntentRecognitionResult.java:38-65` 的小写传输值。
- 改写保留 `related`、`rewritten_question`、`reason`，对应 `prompts/query-rewriting-agent-system.md:10-26`；Python 新增必填 `evidence` 和 `missing_context`，允许未完成改写明确返回 `null`。
- 意图保留 `intents`、`primary_intent`、`multi_intent`、`overall_reason` 和每项的类别/置信度/理由；主要意图只要求属于列表，基线没有“必须在第一项”的约束。依据：`prompts/intent-recognition-agent-system.md:14-36,76-80`。
- Python 去掉模型自由填写的 `target_agent`，新增每项必填证据。Java 提示词使用 lowerCamelCase、枚举默认目标使用 UpperCamelCase、Master 工具注册使用 snake_case，三者并非同一命名契约；本步不增加命名转换或模型驱动的调度捷径。
- Java 内部的 `source`、`score` 未由 `toJsonMap()` 输出（`agent/intent/IntentRecognitionResult.java:119-135,187-193`），本步也不接受它们作为模型输出字段。

这些是 Python 的新数据契约，原 Java JSON 不能未经调整直接输入；不提供旧字段别名或解析失败后把任意文本当作有效结果的兼容入口。标准 JSON 用 `model_validate_json()`，字典用 `model_validate()`，错误统一为 Pydantic `ValidationError`。字段关系使用 [Pydantic 模型验证器](https://docs.pydantic.dev/latest/concepts/validators/)，未知字段通过 [extra 配置](https://docs.pydantic.dev/latest/api/config/)拒绝。

原文概述的“先改写、再识别”不代表当前 Java 每次都这样走：普通请求先尝试原句快速识别，未命中才改写，见 `agent/service/AgentPipelineService.java:139-153`。008 不改变这一后续编排目标。
