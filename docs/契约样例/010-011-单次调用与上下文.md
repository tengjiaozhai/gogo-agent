# 010–011 单次模型调用与跨轮改写上下文

> 已完成独立模块与固定响应验收，2026-09-28。实际使用项目 `.venv` 中的 Python 3.12.13、AgentScope 2.0.8、Pydantic 2.13.5。009 的职责与后续编排顺序见 [调用边界决策](../架构/009-改写与识别调用边界.md)。

## 010：每个操作一次生成

公开入口是 `QueryRewriter.rewrite(RewriteContext)` 和 `IntentRecognizer.recognize(QueryInput)`，返回 008 的 `RewriteResult` 与 `IntentResult`。两个入口只依赖注入的 `ChatModelBase`，共享一次调用和结果校验函数；没有 `Agent` 实例、工具注册或工具循环。

`create_text_model(credential, model_name)` 沿用项目所用 DeepSeek 兼容网关模型，模型名和凭证由调用方提供，不新增环境变量或读取隐式默认凭证。

| 参数 | 当前设置 |
| --- | --- |
| `stream` | `False`，只接受最终 `ChatResponse` |
| `temperature` / `max_tokens` | `0` / `2048` |
| `thinking_enable` | `False` |
| `tools` / `tool_choice` | `None` / `None`，不发送工具定义 |
| `response_format` | `{"type":"json_object"}`，schema 和中文任务说明在系统消息中 |
| AgentScope `max_retries` | `0` |
| 底层 SDK `max_retries` / timeout | `0` / `60` 秒 |

调用方负责关闭工厂所建的 `model.client`。注入的模型若启用了流式、AgentScope 重试，或可见的底层客户端重试，入口会在发请求前拒绝；自定义 provider 自己的传输行为仍由其实现负责。

**错误契约：**

- 非法 JSON、缺字段、不合法的意图/上下文状态，以及非最终响应，抛出 `ModelOutputError`；不截取 Markdown 代码块、不修复 JSON、不再次生成。
- 即使文本看似有效，夹带 `ToolCallBlock` 也被拒绝，工具永远不会在这里执行。
- 模型传输错误原样向调用方传播；SDK 返回中断标记时恢复为 `CancelledError`，不伪装成合法业务结果。
- 错误文案不回显原始模型输出或业务历史。模型语义错误但结构合法的情况，需要后续语料验收，schema 不能证明改写真实正确。

普通模型调用与 `generate_structured_output()` 不同：本地 AgentScope 后者含策略回退，可能多次请求；本次使用普通 `__call__` 并手动做 008 契约校验。核对位置：安装包 `agentscope/model/_base.py:182-217,457-477`、`model/_deepseek/_model.py:79-136,185-231`。测试同时覆盖真实 SDK 的成功、429 和 500 请求，确认没有隐藏重试。

## 011：先存本轮，再构造历史快照

调用方式：

```python
message_id = history_service.save_user_message(session_id, user_id, question)
context = RewriteContextBuilder(history_service).build_rewrite_context(
    session_id, user_id, current_message_id=message_id
)
rewrite_result = await QueryRewriter(model).rewrite(context)
if rewrite_result.rewritten_question is not None:
    intent_result = await IntentRecognizer(model).recognize(
        QueryInput(question=rewrite_result.rewritten_question)
    )
```

`user_id` 应来自已验证的登录上下文。这里展示独立模块的使用顺序，不表示 HTTP 当前已经调用这些步骤。

上下文构造规则：

1. 通过 `ChatHistoryService.get_history_messages` 校验会话存在且属于当前用户，再查询领域消息；HTTP 的 `list_messages` 也委托给这个鉴权入口。跨用户返回 403，不读取该会话的消息正文；不存在/已删除会话返回 404。
2. 取最近 **11 条未删除记录**，分离其中本轮用户消息，余下最多 **10 条历史消息**，不是 10 轮对话。SQL 在数据库内 `ORDER BY ... DESC LIMIT 11` 后反转；内存仓储遵守相同次序。
3. 默认以最后一条为本轮；建议始终传入 `save_user_message()` 返回的 ID，尤其是数据库时间精度导致多条消息同时刻时。显式 ID 必须位于最新时间窗口并且是用户消息，否则 409。按 ID 分离本轮，不按文本去重，历史中相同内容的另一次发言保留。
4. 没有较早历史但本轮已保存时，`history=[]`，仍可调用改写处理自包含问题或显式报告缺上下文。没有保存本轮、末尾已是助手回复或消息 ID 过时则明确失败；历史读取异常继续向上传播，不当作“无历史”。
5. 历史字符预算默认 **8000**，可由 builder 构造参数调整；从最新消息向前保留，预算边界处保留该消息尾部，删除更早内容。字段 `truncated` / `history_truncated` 明示裁剪，空白历史不发送。
6. 当前问题只做 008 的首尾空白规范化，不参与历史裁剪。参考日期由服务端按 `Asia/Shanghai` 生成，也可显式注入固定 `reference_date` 以复现样例。预算计文本字符，不是模型 token，schema 和本轮问题还会占上下文。

**时间顺序的现有边界：**排序键是 `(created_at, message_id)`，后一个只用于同时刻记录的稳定排序，随机 ID 不能恢复实际写入先后。构造器直接比较领域消息时间，不经过 HTTP 毫秒时间戳；数据库本身已丢失的时间精度无法补回，完全同时刻时依赖调用方传入的本轮 ID。当前支持同会话按保存→构造→执行的串行用法；并发新消息、多实例快照一致性与已有低精度历史的真实先后尚未在本步解决，按 022/后续持久化工作验收。未对实际 MariaDB 执行 schema 修改。

Java 当前 `buildRewriteInput` 实际查询 `RECENT_MESSAGE_LIMIT + 1`，没有再次追加 `inputMessages`。其加载失败分支会返回空历史，且查询没有 `user_id` 校验；本次保留正常窗口语义，沿用 Python 005 已有的所有权校验并显式传播失败。证据：Java `AgentPipelineService.java:623-648`、`business/chat/service/ChatHistoryService.java:71-77`；Java 根目录见 009 决策记录。

## 三轮固定对话验收

参考日期固定为 `2026-09-27 / Asia/Shanghai`。前两轮复用 [008 JSON 样例](008-两轮对话.json)，第三轮在针对性测试中追加。

| 轮次 | 当前问题 | 固定期望改写的关键内容 |
| --- | --- | --- |
| 1 | 规划9月30日北京到杭州的两天出差，包含往返交通和酒店 | 信息完整，保持原句；没有历史也能处理。 |
| 2 | 明天去上海呢？ | 9月28日，北京→上海、两天、交通和酒店；任务仍是规划。 |
| 3 | 改成三天，那边的酒店也重新选一下。 | 延续9月28日和最新目的地上海，改为三天并重新选择酒店；不回到旧目的地杭州。 |

测试先把每轮用户消息和不同角色的答复写进业务仓储，再构造上下文。模型替身记录实际收到的历史、角色与日期，并返回固定结果；因此它证明消息传递、参数、校验和调用次数，**不证明真实模型已经具备上述理解质量**。另有新话题保持原句、缺历史返回未完成、历史 system 仅作数据等案例。

无需改写时，模型在一次判定中给出原句后直接返回，不再发起第二次生成。本模块不靠指代关键词表猜测是否跳过模型；快速层命中时跳过整个改写步骤的逻辑在 012–017 实现。
