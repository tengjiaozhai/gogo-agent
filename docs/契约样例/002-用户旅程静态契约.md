### 2. 新对话、聊天与挂起恢复

- **脱敏输入**：前端先在本地创建 `session_<时间戳>` 和标题“新对话”，没有独立的创建会话 HTTP 请求；首次发送 `POST /api/chat/session_<占位>`，Header `Authorization: <token>`、`Content-Type: application/json`，Body `{"message":"你好，请介绍可用功能"}`。后端从登录态取得 `userId`，不是从 Body 取得。来源：`frontend/src/store/chatStore.ts:99-112`、`frontend/src/api/chat.ts:9-29`、`controller/ChatController.java:54-63`。
- **状态、响应与事件**：Controller 返回 `SseEmitter`；HTTP 握手状态未观测。静态可确认的完成事件顺序为 `event: message`（回复文本）、落库成功后 `event: message_id`（`msg_<不透明ID>`），正常完成后可能有 `suggestions`；失败分支可发 `error` 并结束流。执行中还可能有 `progress`、`thinking`、`plan_update`、`travel_data`、`plan_html`、`booking_result`、`user_interaction`。这些是**可能的事件类型**，不是本次已观测的事件流；消息文本与事件出现情况取决于实际执行。前端按空行分隔 SSE，并合并同一事件的多行 `data:`。来源：`agent/service/ChatAgentExecutor.java:323-359`、`agent/service/ChatSseNotifier.java:37-89,104-147`、`frontend/src/api/chat.ts:40-80`、`agent/hook/BookingPersistenceHook.java:242-254`。
- **数据副作用与风险**：第一条消息在会话不存在时写入 `chat_conversation`，再写 `chat_message`；默认标题被首条非空消息开头替换（最多 24 字）。回复也尝试落库；两处落库异常被捕获后仍可能继续 SSE，因此流成功不保证历史完整。该请求还会调用模型，若意图进入业务 Agent，可能触发后文写操作；演示时只使用隔离用户和只读问题。来源：`business/chat/service/ChatHistoryService.java:80-108,199-219`、`controller/ChatController.java:65-75`、`agent/service/ChatAgentExecutor.java:327-335`。
- **挂起补充入口**：若收到 `user_interaction` 及 `toolUseId`，前端可向 `POST /api/chat/respond` 发送 `{"sessionId":"session_<占位>","toolUseId":"<占位>","response":"<脱敏回答>"}`，控制器调用 `agentExecutor.resume` 并返回 SSE；此分支未运行。来源：`controller/ChatController.java:114-133`、`controller/request/ChatRespondRequest.java:8-35`。

### 3. 差旅单与本地审批申请

- **脱敏输入**：用户仍通过 `POST /api/chat/{sessionId}` 说明出发地、目的地、日期和事由；若 Agent 调用 `submit_travel_approval`，内部工具参数为 `destination`、`departure_city`、`departure_date`、`return_date`、`purpose`（日期格式 `YYYY-MM-DD`）。没有差旅单创建的独立 HTTP 路由。`userId` 取自服务端会话上下文。来源：`agent/ItineraryManageAgent.java:25,47`、`agent/tools/TravelOrderWriteTools.java:115-123`、`controller/ChatController.java:54-58`。
- **状态与静态输出**：HTTP 仍是上面的 SSE，未观测状态码或最终回复。工具校验空字段和日期范围，成功时内部结果含 `success`、`orderId`、`processInstanceId` 和状态；不能据此断言 SSE 直接发送同样的 JSON。随后可用 `GET /api/my-travel/orders` 按当前用户查询列表；该 Controller 返回数组，每项含 `orderId`、目的地、日期、`status`、最新审批信息及 `bookings`，HTTP 200 只按普通返回推定，未实测。来源：`agent/tools/TravelOrderWriteTools.java:126-157,170-190`、`controller/MyTravelController.java:117-135,222-266`。
- **条件与写入风险**：需要隔离 MySQL；`createAndSubmit` 在同一事务中写 `DRAFT` 差旅单、`PENDING` 审批单，再把差旅单改为 `SUBMITTED`。工具先查相同用户和行程要素的生效中差旅单以避免重复创建。这是本地数据库写入，不等于外部钉钉审批已提交。来源：`business/order/service/TravelOrderService.java:52-75`、`agent/tools/TravelOrderWriteTools.java:160-190`、`business/approval/service/ApprovalService.java:31-44`。

### 5. 行程方案审核与管理员审批

- **脱敏输入（方案审核）**：经聊天请求调用 `ItineraryReviewTools.review_itinerary`，内部参数含 `origin`、`destination`、`departure_date`，其他政策、天气、资讯、偏好参数可选。无独立方案审核 HTTP 路由；独立 `ItineraryReviewAgent` 已标 `@Deprecated`。来源：`agent/ItineraryPlanAgent.java:76`、`agent/tools/ItineraryReviewTools.java:94-113`、`agent/ItineraryReviewAgent.java:33`。
- **方案审核的输出与副作用**：工具从当前用户规划 Redis 读取方案，缺失时返回失败报告；有方案时执行客观校验与主观模型评估，返回审核报告 JSON，并按 session 保存上一轮报告。HTTP/SSE 状态和报告内容未实测。需要隔离 Redis 与模型调用；不产生管理员审批决定。来源：`agent/tools/ItineraryReviewTools.java:130-171`。
- **脱敏输入（业务审批）**：管理员用 `Authorization: <管理员token>` 查询 `GET /api/admin/approvals?status=PENDING`；决定时发送 `POST /api/admin/approvals/pi_<占位>/decision`，Body `{"decision":"agree","remark":"<脱敏备注>"}`。列表与决定成功都通过 `ResponseEntity.ok` 返回含 `processInstanceId`、`status`、`orderId`、`form` 等字段的视图；非法 `decision` 明确为 400、非管理员 403、审批单不存在或已处理为 409。未运行，以上状态来自 Controller 分支。来源：`controller/AdminApprovalController.java:45-106,123-129`、`controller/request/ApprovalDecisionRequest.java:8-13`。
- **业务审批写入风险**：管理员角色由登录用户的 `user_account.role` 校验。`decideAndSyncOrder` 在事务中更新本地审批与差旅单状态为 `APPROVED` 或 `REJECTED`；不会主动推送给 Agent 会话。该操作会改写业务数据，本文未执行。来源：`business/auth/service/AuthService.java:59`、`business/order/service/TravelOrderService.java:151-170`、`controller/AdminApprovalController.java:81-90`。

### 6. 预订

- **脱敏输入**：用户经 `POST /api/chat/{sessionId}` 确认具体方案后，`BookingAgent` 可调用 `tuniu-cli` 技能。提示词要求先执行 `check_travel_order_approval`，未通过则拒绝预订；实际机票、火车和酒店下单分别使用途牛 CLI 的 `saveOrder`、`bookTrain`、`tuniuHotelCreateOrder`。没有独立创建预订的 HTTP 路由。**审批检查是当前 Agent 提示词要求，不据此推断已存在不可绕过的服务端写入门禁。**来源：`agent/BookingAgent.java:65-110`、`prompts/booking-agent-system.md:13-27`。
- **状态与静态输出**：HTTP 仍为聊天 SSE，未运行供应商请求，不能填“下单成功”的实测状态。若 CLI 成功返回外部单号，`BookingPersistenceHook` 保存预订记录后发送 `booking_result`，静态 payload 含 `bizType`、`orderId`、`amount`、`currency`、`payUrl` 等；`MyTravelController` 的 `GET /api/my-travel/orders` 再聚合预订摘要。来源：`agent/hook/BookingPersistenceHook.java:146-208,242-254`、`controller/MyTravelController.java:258-284`。
- **条件与外部写入风险**：必须具备隔离测试账户、已通过的差旅审批、途牛 CLI/API Key 与完整旅客资料。该代码路径会向真实途牛远端提交个人资料和订单，并写本地预订数据库，不能当作模拟下单；现有 Hook/工具单测使用固定响应且未调用真实 CLI。本项仅记录契约，**没有执行预订**。来源：`skills/tuniu-cli/SKILL.md:91-104`、`agent/hook/BookingPersistenceHook.java:182-208`、`src/test/java/com/gogo/travel/agent/hook/BookingPersistenceHookTest.java:140`、`src/test/java/com/gogo/travel/agent/tools/BookingWriteToolsTest.java:29-32`。
