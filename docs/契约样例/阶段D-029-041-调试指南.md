`demo_029_040_stage_d.py` 可逐项运行，例如 `--case 029` 或 `--case 035`。每个 case 都新建隔离 SQLite，预置 Alice (`u001`, P6) 和 Bob (`u002`, P5) 的**可信职级**。031、035、038 会先用 `submit()` 建 Alice 的订单；037 插入一条模拟酒店预订；036 只构造内存行程片段，不建订单。`all` 不共享前一 case 的订单。日志中的 `order_id`、`approval_id`、`trace_id`、时间和耗时每次会变化；状态、工具名、错误码与布尔值稳定。

PyCharm 配置：Script path 选 `scripts/demo_029_040_stage_d.py`，Working directory 选本仓库根目录，Interpreter 选 `.venv/bin/python`，Parameters 先填 `--case 035`，Environment 填 `PYTHONPATH=src;GOGO_DATABASE_URL=`。034 与 041 换对应脚本；041 离线演示无参数。真实网关测量才用 `--live`，会发六次模型请求，不读写业务库。

`RequestContext` 是服务端构造的冻结身份快照；闭包 `ask_manage_agent` 捕获它，类似 Java `AgentSessionContext` 旁路注入，但不是模型参数。`async def`/`await` 让主 Agent 等子 Agent 回答；`asyncio.timeout` 限制一次子 Agent 委派；`finally` 无论成功与否都关闭模型客户端。`with self.repository.transaction()` 在 `yield` 正常退出时提交，异常时回滚，作用类似 Java 的 `@Transactional`，但 SQLAlchemy Session 生命周期由 Python 上下文管理器显式控制。`Field(..., description=...)` 同时限制 Pydantic 输入并生成 API 文档；ORM `comment=` 是数据库列语义，不能取代请求校验。`Decimal` 避免酒店金额用二进制浮点比较。

订单与审批状态由服务函数控制，转移表如下。`COMPLETED` 仅保留为 Java 兼容的只读终态，本阶段没有完成行程的写接口。

| 操作 | 允许的订单/审批前态 | 后态 | 必须满足 |
| --- | --- | --- | --- |
| 新建并提交 | 无相同活跃申请 | `DRAFT` 暂态 → `SUBMITTED`；新审批 `PENDING` | 本人确认、幂等键、完整日期字段；订单/审批/审计同事务。 |
| 修改并重提 | `DRAFT`、`SUBMITTED`、`REJECTED`，或 `APPROVED` | `SUBMITTED`；旧审批 `CANCELLED`，新审批 `PENDING` | `APPROVED` 还需 `force=true`；先锁订单再锁旧审批。 |
| 取消申请 | `DRAFT`、`SUBMITTED`、`REJECTED`，或 `APPROVED` | `CANCELLED`；当前审批 `CANCELLED` | `APPROVED` 还需 `force=true`；重复同键只重放已保存结果。 |
| 管理员同意/拒绝 | 订单指向当前 `PENDING` 审批 | `APPROVED`/`REJECTED`；审批同名状态 | 必须管理员身份，先锁订单再锁审批并在同事务同步；拒绝后释放活跃申请唯一键。 |
| 非法或终态改动 | `CANCELLED`、`COMPLETED` 或非当前审批 | 保持原值 | 返回状态冲突，不生成新审批。 |

## 先预测，再核对

1. `--case 031` 中让模型在问题文本写 `user_id=u001`，Bob 能拿到 Alice 的单吗？**不能。** 工具 schema 只接收 `order_id`，闭包内 `user_id` 固定为认证的 `u002`，仓储再次按 owner 过滤。可运行 `PYTHONPATH=src GOGO_DATABASE_URL='' .venv/bin/python scripts/demo_029_040_stage_d.py --case 031` 核对 `ORDER_NOT_FOUND`。
2. P6 上海酒店金额恰好 500、500.01 和缺失时合规吗？**依次是合规、不合规、不合规。** 运行 `--case 032`，在 `check_policy()` 看 Decimal 比较。文档片段相似度再高也不改变精确规则。
3. Alice 的已审批差旅单不传 `force` 直接修改会怎样？**409 `FORCE_CONFIRMATION_REQUIRED`，审批不动。** `tests/test_030_038_travel_business.py` 覆盖该分支；传 `force=True` 才能撤销旧审批并生成新的 `PENDING`。
4. 酒店本地取消成功能否告诉用户“酒店供应商订单已取消”？**不能。** `--case 037` 返回 `supplier_cancelled=False` 和联系酒店提示；机票/火车默认适配器拒绝外部取消。
5. 政策语料改完后旧进程的索引会自动刷新吗？**不会。** `demo_034_policy_knowledge.py` 显式重建文件并重新创建 `PolicyKnowledgeIndex`；正式进程需重新装配服务，精确额度规则另由 `policy_seed.json` 控制。

## 041 原始测量与配置结论

2026-10-07 使用当前 `.env` 的 `deepseek-v4-flash-0731` 和 `scripts/benchmark_041_thinking.py --live`，对同三题依次跑默认参数和 AgentScope `thinking_enable=True, reasoning_effort="high"`。每题只发一次，无真实工具执行。结果：

| 模式 | 题目 | 耗时 ms | JSON 有效 | 虚构工具调用 |
| --- | --- | ---: | --- | ---: |
| default | policy_read | 2090.4 | 是 | 0 |
| default | order_write | 2973.7 | 是 | 0 |
| default | planning | 2357.7 | 是 | 0 |
| high | policy_read | 1562.8 | 是 | 0 |
| high | order_write | 2007.2 | 是 | 0 |
| high | planning | 1659.4 | 是 | 0 |

六次样本只证明网关接受两组请求、该次输出满足最小 JSON 契约且未请求虚构工具。运行顺序未随机化，无法据此推断高推理一定更快；网关是否实际启用了推理也未从服务端响应证明。现有 GoGo、Manage、Info、推荐角色显式保持 `thinking_enable=False`，政策和订单规则由服务端函数判断。Java 的规划/执行/总结 Hook 需等阶段 E 的 PlanAgent 存在后，针对真实阶段输出和延迟再决定是否迁移。

## 2026-10-07：`.env` 数据库建表记录
