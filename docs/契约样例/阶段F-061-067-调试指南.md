### 1.3 本编号用到的 Python 语法与对象生命周期

- **`Protocol`**：`SupplierGateway` 描述形状，不需要 `implements`。`SimulatedSupplier` 只要有同名方法即可替换真实适配器。
- **`asyncio.Semaphore` 与 `async with`**：`search_in_parallel` 中 `async with semaphore:` 在进入时获取许可，退出时释放；与 Java `Semaphore.acquire/release` 相似，但退出由语法保证。
- **`asyncio.timeout`**：超时上下文，超时抛出 `TimeoutError`。它不是 try-with-resources。
- **`CancelledError` 是 `BaseException`**：`except Exception` 不会捕获它。`ToolBreakerRegistry.call` 单独处理取消，释放半开探测位；若没有这段代码，熔断会永久停在探测中。
- **`with repo.transaction() as session`**：这是 `contextmanager` 生成器，`yield` 之前开始事务，退出时提交或回滚。它与 Java `@Transactional` 的边界相似，但在代码中显式可见。
- **事务内快照**：`_load` 在事务内取出字典，而不是返回 ORM 对象。事务结束后访问 ORM 对象可能因会话状态而报错。
- **`lambda` 闭包**：`lambda: self.supplier.lookup(booking_id)` 捕获 `booking_id`，供 `call_read_with_retry` 重复调用。
- **`Decimal`**：金额用 `Decimal(f"{x:.2f}")` 构造，避免浮点误差；Java 对应 `BigDecimal`。
- **只相似不等价**：Java 的 `Tool execution failed` 是文本判定，Python 是异常判定；Java 的冷却会倍增，Python 不会。

## 3. 练习：先预测，再运行

**E1（062）**：不传 `confirmed=True` 时，供应商调用次数是多少？
- 答案：0，错误码为 `CONFIRMATION_REQUIRED`。
- 验证：`--case book` 第一行。

**E2（066）**：供应商已生成订单但响应丢失，结果是什么？
- 答案：`CONFIRMED`，供应商创建调用 1 次。对账查询找到同一请求 ID 的订单，不会再创建第二单。
- 验证：`--case lost` 第一行。

**E3（066）**：订单没有生成且响应丢失，连续两次调用会怎样？
- 答案：两次都是 `UNKNOWN`，供应商创建调用仍为 1 次，本地状态为 `CREATED`。系统不宣称成功，也不自动重建订单。
- 验证：`--case lost` 第二行。

**E4（067）**：`query_weather` 连续失败 3 次后，第 4 次调用会怎样？
- 答案：抛出 `CIRCUIT_OPEN`，外部调用次数仍为 3。
- 验证：`--case breaker` 第一行。

**E5（067）**：冷却后的探测失败，状态是什么？
- 答案：`OPEN`，外部调用次数变为 4。探测失败会重新打开熔断，并重新计时。
- 验证：`--case breaker` 第二行。

**E6（063）**：酒店供应商侧订单已经不存在，取消会怎样？
- 答案：抛出 `SUPPLIER_CANCEL_FAILED`，本地状态保持 `CONFIRMED`。取消顺序是先供应商、后本地，因此供应商失败时本地不会被误改。
- 验证：`tests/test_061_067_booking.py::test_063_hotel_cancel_calls_supplier_first_and_keeps_local_state_on_failure`。

**E7（064）**：重新计算方案后，能否再次预订同一行程段？
- 答案：不能，旧订单仍为确认状态时返回 `BOOKING_ALREADY_CONFIRMED`。先取消旧订单后，新的内容版本可以下单。
- 验证：`tests/test_061_067_booking.py::test_064_replanned_leg_cannot_book_twice_until_old_booking_is_cancelled`。

**E8（061）**：预订 Agent 能否修改审核结论或直接下单？
- 答案：不能。它的工具只有 `prepare_booking` 和 `query_booking`，前者只返回待确认摘要。
- 验证：`tests/test_061_067_booking.py::test_061_booking_toolkit_has_no_writable_tool_and_no_plan_or_review_mutation`。

**已知缺陷与限制**

- **多段预订不是原子操作**：一次方案包含去程、酒店、返程三段，需要分别调用。若去程成功、返程被拒绝，系统不会自动补偿，需要用户或运营人员处理。
- **未知结果没有后台对账**：`CREATED` 且 `UNKNOWN` 的记录只在同一业务键再次调用时重新查询，没有定时任务。
- **酒店取消的审计差异**：阶段 D 的审计结果对酒店仍记录 `supplier_cancelled=false`；`BookingService.cancel` 返回的结果以供应商侧为准，两者不一致。
- **回调未实现**：没有供应商回调入口，因此回调事件 ID 的去重只覆盖同步响应和对账查询。
- **聊天路由未接入**：预订 Agent 没有接入 HTTP 对话；097 的结构化确认尚未实现，`confirmed=True` 只能由服务端调用方传入。
- **熔断未接入生产客户端**：`ToolBreakerRegistry` 需要调用方显式使用，`DestinationLiveClient` 的生产路径没有包装。
- **生产等待**：对账重试在生产环境使用 `time.sleep`，测试注入了空操作。
- **数据库**：没有新增表，沿用阶段 D 的 `booking_record` 与 `business_action_audit`；只在 SQLite 中验证，未在 MySQL 中运行。
- **真实服务**：没有连接任何真实供应商，也没有运行 Java 应用。
