# 028 工具身份与 SQL 会话归属

## 先运行

从 Python 仓库根目录运行；缺少 `.venv/bin/python` 时先执行 `uv run --locked gogo-agent --health` 准备环境。本例只使用内存测试 Token、固定模型与内存 SQLite：

```sh
PYTHONPATH=src .venv/bin/python scripts/demo_028_trusted_identity.py --case all
```

`--case tool` 只跑模型伪造工具参数；`--case sql` 只跑删除后复用会话 ID；`all` 先 tool 再 sql，两个场景各自新建状态，无隐藏前置网络轮次。预期 tool 输出 `模型可见工具参数：['question']`、Bob 读取 Alice 会话为 `HTTP 403`，模型传入的额外 `userId/sessionId/planReference` 被 AgentScope 工具参数校验拒绝；sql 输出 Bob 复用写入为 `403`，Alice 可继续使用原会话，Bob 读取仍为 `403`。本例的本地会话名固定，真实 Token、request ID 和 trace ID 每次不同。

PyCharm：Script path 设本仓库 `scripts/demo_028_trusted_identity.py`，Working directory 设本仓库根目录，Interpreter 设 `.venv/bin/python`，Environment 设 `PYTHONPATH=src`，Parameters 先填 `--case tool`，再改成 `--case sql`。若 IDE 不识别相对 `src`，填其绝对路径。两个场景不会连接 Java 工程或远端 MySQL。

## 谁能决定 userId

| 数据 | Java 基线 | Python 当前实现 |
| --- | --- | --- |
| 登录身份 | `ChatController` 从 Sa-Token 取 `userId`，`AgentSessionContext` 在构造时固定；工具通过 `ToolExecutionContext` 旁路拿身份 | [`auth/dependencies.py`](../../src/gogo_agent/auth/dependencies.py) 从 Token 得到 `UserAccount`；HTTP Router 传 `user_id` 给 [`ChatAgentExecutor`](../../src/gogo_agent/chat/executor.py)，保存用户消息且校验会话归属后创建冻结的 `RequestContext`。 |
| 模型可填的工具字段 | `BaseSubAgent.createToolCtx()` 不把注入的 `userId/sessionId` 放进工具 schema | 当前唯一生产 HTTP 工具 `info_agent` 的 schema 只有 `question`；闭包捕获可信 `RequestContext`，`InfoAgent` 无业务读取/写入工具。模型即使额外输出 `userId` 也不能覆盖闭包身份。 |
| 会话与业务记录归属 | Java 部分差旅/预订工具有 userId 条件或事后所有权比较；Java 聊天保存与 `/respond` 的 owner 校验并不完整 | Python 会话服务对已有 session 校验登录用户；SQL 新建/复用已删除 ID 时重新写入 owner，保存用户消息前再确认实际 owner。未实现的计划/差旅业务仓储仍须在未来编号独立验证。 |

“模型不知道 userId”不能理解成用户原文中不可能出现 `userId`：用户可以输入任意伪造文本，模型也可以输出额外 JSON 字段。安全边界是**工具 schema 不向模型索取身份、服务端不采信模型自报值、仓储最终按认证用户验证归属**。Python 用闭包和显式参数传 `RequestContext`，Java 用框架的 ToolExecutionContext；两种注入机制的生命周期不同，目的相同。`await` 等待当前 Agent/工具完成，不等于 Java Reactor 的订阅。`tool` 场景的 `@asynccontextmanager` 管理固定模型作用域，`yield` 之后关闭模型客户端；正式请求还有 Qdrant/模型资源生命周期。

## 按顺序单步

| 场景与命中 | 断点位置 | 进入前变量 | 下一步应看到 |
| --- | --- | --- | --- |
| `tool` 第 1 次 | `scripts/demo_028_trusted_identity.py` 的 `tool_case()` 中 Alice 的 `client.post()` | Alice Token、路径 `alice-028`，模型待输出 `userId=u002` 等额外参数 | `get_current_user()` 返回 `u001`；`_save_user_turn()` 的 `request.user_id` 是 `u001`，`request.plan_reference=None`。 |
| `tool` 第 1 次模型调用 | `ForgedMasterModel._call_api()` 中创建 `ToolCallBlock` | `tools[0].function.parameters.properties` 仅有 `question` | AgentScope 对额外身份参数给出工具参数错误；`build_info()` 不被调用，也不写活跃记录。若未来 SDK 改为允许多余字段，服务端闭包仍只能使用 Alice 的 `request`，届时须重验负例。 |
| `tool` Bob 读历史 | `ChatHistoryService.get_history_messages()` 的 owner 比较 | 路径 `alice-028`，Token 用户 `u002` | 返回 403，不读取 Alice 消息；Bob 的 active-agent 键为空。 |
| `sql` Alice 删除 | `ChatHistoryService.delete_conversation()` | SQL 会话 owner `u001`、旧消息未删除 | 先将消息标记删除，再将会话标记删除；该 ID 可以作为新会话重新使用。 |
| `sql` Bob 复用 | `SQLChatHistoryRepository.save_conversation()` 的已删除行归属检查；接着 `ChatHistoryService.save_user_message()` 的 `PermissionError` 转 403 | 查询到已删除旧行、旧 owner `u001`；新请求用户为 `u002` | 保留原 owner `u001`，Bob 不能保存；Alice 可以继续使用该 ID，旧消息仍标记删除。 |
| `sql` Alice 再读 | `ChatHistoryService.get_history_messages()` | 现行 owner `u002` | Alice 得到 403；不会读到 Bob 的新消息。 |

预测练习：在运行前先回答：模型在 tool-call JSON 中填 `userId=u002` 会改变 `RequestContext.user_id` 吗？Bob 可否读取 Alice 的 `sessionId`？若 SQL 的已删除会话主键被 Bob 重新使用，原行 owner 是否改变，旧消息能否重新可见？再运行 `--case tool` 和 `--case sql` 核对。答案依次为“不变、不能、不改变、不能”。当前没有计划仓储或计划读取工具，所以伪造 `planReference` 只证明它没有进入 `RequestContext`；后续引入计划 ID 时必须在仓储查询/写入边界增加 owner 条件和跨用户负例。

测试见 [`test_028_identity_boundary.py`](../../tests/test_028_identity_boundary.py)；SQL 复现使用真实 SQLAlchemy/SQLite 语义，工具部分使用真实 FastAPI 和 AgentScope Toolkit，模型响应为固定替身。未验证远端 MySQL 的并发事务、未来计划与预订工具或供应商写操作。
