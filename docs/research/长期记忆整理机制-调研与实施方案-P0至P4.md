## 一、结论

1. 调研只覆盖两套系统：Codex memories 子系统与 ReMe Auto Dream。WeKnora、Mem0 V3、Graphiti、Hindsight、Letta、Claude Code 没有进入结论。
2. “让新事实更新或纠正旧记忆”的证据最弱。工作流没有确认任何 superseded / archived 状态机或版本号。本地核对发现 ReMe 文档列有 `CORRECT` 动作，但未说明旧内容是否保留。
3. ReMe Auto Dream 处理的是 `daily/` 目录；本项目的自动记忆写在 `digest/users/<hash>/`，二者当前不交互。因此 F1–F5（§3.1）是**设计参考**，不是本项目运行时的依赖。
4. 当前实现的三个问题，直接对应调研结论：静默截断（P1）、无条件的整文件覆盖（P0）、失败即丢失（P3）。推断：这三项都可以在不引入图谱或多 Agent 的前提下修复。
5. 推荐顺序：P0 → P1 → P3 → P2 → P4。P0、P1、P3 不依赖模型判断，可先做；P2 需要先建样例集；P4 可选。

### 3.2 本地核对（2026-11-16）

- `reme/steps/evolve/dream/finish.py:34` 的 checkpoint 公式为 `changed ∩ processed − failed`，与 F2、F3 一致。
- `docs/zh/auto_dream.md` 的整合动作表为 `CREATE / CORROBORATE / REFINE / CORRECT`，并要求“新增与更新都必须保留来源”。文档级依据成立；`CORRECT` 是否保留旧内容未说明，实现未核。
- `/help` 声明 `save` 接受 `expected_mtime`。`/stat` 返回的 mtime 为 ISO 微秒字符串（如 `2026-11-15T13:40:46.495873`），与 `save.py` 中 `datetime.fromtimestamp(...).isoformat()` 的比较格式一致。（只读调用，目标为 `digest/users/992ab96f91850cb7/auto-memory.md`。）
- `save.py` 的文档字符串写明“不解释、不重建 frontmatter”；`write.py` 则按 `name`/`description` 生成 frontmatter。切换到 `/save` 后，frontmatter 必须由本项目代码生成。
- `save.py:40` 的检查是 `if expected_mtime and current_mtime != …`。文件不存在时 `current_mtime` 为 `None`；若调用方不传 `expected_mtime`，检查整体跳过。因此并发**创建**同一用户文件时没有保护。
- `reme.py:49` 与 `:61`：语义召回的请求带 `search_filter.prefix`，返回后再按同一前缀过滤。因此 `digest/users/<hash>/` 之外的文件不会被召回。

## 四、设计原则

以下五条由 GoT 聚合得出，括号内为依据：

1. **条件写**：写入前校验版本（mtime 或 version），冲突则重读、重合并（F6；ReMe `save.py:40`）。
2. **提交点在后**：水位、基线、成功记录，在持久化成功之后推进（F8 为反例；F2 的 checkpoint 规则）。
3. **显式计数**：截断、丢弃、跳过都计数并记日志，不允许静默（F3 为反例）。
4. **被替代不等于删除**：旧值移入历史文件，但不参与召回（`reme.py:49、61`）。
5. **不确定性保留**：证据冲突且无法判断先后时，两条并存并标注 `conflict`，不能用新证据直接覆盖。Codex 整理提示有同类规则：“If evidence conflicts and validation is unclear, preserve the uncertainty explicitly.”（`consolidation.md` 349，main 分支；译文：证据冲突且验证不清时，明确保留不确定性）。

本机 wiki 中的相关页面：`wiki/concepts/快慢路径.md` 的判据二指出，门禁信号与慢路径不同源时不应做快路径。向量相似度与“是否该更新旧记忆”不是同源信号，因此 P2 不把向量相似度当作更新判据。`wiki/concepts/意图识别分层.md` 把同类问题列为反面典型。

## 五、实施方案

### P0 条件写（并发安全）· 可立即做

**目标**：同一用户的多个进程或 worker 并发写入时，不丢失更新。

**改动**：
1. `_read_existing`（:146）先调 `/stat` 取 `metadata.mtime`，再调 `/read` 取内容。顺序固定为 stat → read：即使读取期间发生写入，保存时的 mtime 校验也会失败并触发重试。
2. `_write_body`（:161）改为调 `/save`，并传入 `expected_mtime`。`/save` 不重建 frontmatter，因此代码需渲染完整文本：`---`、`name: auto-memory`、`description: …`、`---`，再接正文。
3. 收到 `file_conflict`（`save.py:41-47`）时，重读、重合并、重保存，最多 3 次。超过上限交给 P3 记账。
4. `_lock_for`（:178）保留，只覆盖同进程；跨进程依赖条件写。

**已知限制**：文件不存在时没有 `expected_mtime`，两个进程并发**创建**同一用户文件仍会互相覆盖（§3.2）。若要覆盖创建竞争，可把 P4 的 Redis 租约前移到每次读-合并-写（推断，未实测）。

**验收**：
- 两个进程对同一用户并发写入 N 条不同事实，最终条目数等于不重复事实数。
- 注入 mtime 变化时，触发重读与重试，且不超过 3 次。
- 测试：沿用 `tests/test_reme_recall.py` 中 `reme_base_url` 的做法（在临时 workspace 启动本机 `reme`），不连接 121。

### P1 显式计数（不静默丢弃）· 可立即做

**目标**：每次截断与丢弃都有计数与日志；溢出内容不丢失。

**改动**：
1. `normalize_facts`（:60-82）：超过上限的候选不再 `break`，改为计数 `dropped_over_limit` 并记日志。
2. `merge_facts`（:85-105）：被 `stored[-limit:]`（:102）挤出的行写入 `history/users/<hash>/auto-memory-history.md`。该路径不在 `digest/users/<hash>/` 之下，因此不会被语义召回。
3. `merge_facts` 返回值增加 `evicted` 计数，调用方记日志。签名变化需同步调用方（:214）与 `tests/test_reme_auto_memory.py` 的两处调用（:62、:74）。
4. history 写入同样使用 P0 的条件写。

**验收**：
- 单元测试：超过上限的候选计数正确；超过 `limit` 的旧行出现在 history 中。
- 在临时 ReMe 实例上验证：history 文件不出现在 `search_filter.prefix` 的结果中。

### P2 结构化更新（需先建样例集）· 动作集合已定，待样例验证

**目标**：同义合并、偏好反转时，旧条目被替代，且替代可追溯。

**存储形态**：单文件。`digest/users/<hash>/auto-memory.md` 只保存 active 条目，召回直接读取，行为不变。被替代或被挤出的条目移入 `history/users/<hash>/auto-memory-history.md`（P1 已有该路径），不在检索前缀下，不参与召回。状态由位置决定，不设 `status` 字段，也不引入第二个 JSON 状态文件（避免双写一致性问题）。每行末尾用 HTML 注释记录元数据，例如 `- 2026-11-15 用户出差坐飞机只选靠过道座位 <!-- id:a1b2c3 src:r-42 -->`。`id` 在 ADD 时由内容哈希生成，REFINE 时保持不变，供模型引用。`src` 取自 `RequestContext` 的 `request_id`。迁移：无注释的旧行首次读取时生成 `id`，`src` 留空；alice 现有 2 行无需人工处理。

**动作集合**：`ADD` / `NOOP` / `REFINE` / `REPLACE`。
- `ADD`：没有对应的旧条目；矛盾但无明确改口时也走 ADD，两条并存并带各自日期，由模型结合问题判断。
- `NOOP`：与某条 active 实质相同。
- `REFINE`：补充条件或细节，原条目内容更新，旧内容写入 history。
- `REPLACE`：旧条目移入 history，新条目取代。仅在守卫通过时执行（见下）。

**REPLACE 守卫**：代码只在本轮用户原话含明确改口词（如“以后”“改成”“不再”“换成”）时执行 REPLACE，否则降级为 ADD。已知代价：只说“最近更喜欢靠窗”而无改口词时，旧“靠过道”仍保留，这是“偏好反转”的部分缺口。样例集须包含“反转但无改口词”用例，统计漏判率；漏判率高时再放宽触发条件（由模型判断、代码只校验 id）。

与调研草案相比：去掉 `ARCHIVE`（本项目只记长期偏好，抽取提示词已禁止一次性行程，无事项过期场景）；去掉 `CONFLICT`（矛盾无改口时以 ADD 保留两条带日期的记录；只有样例证明答错率高时才重新引入）。

**决策者**：轻量模型，每轮一次调用。输入为现有 `active` 条目（带 `id`）与本轮 Q/A。输出 JSON：`{"actions": [{"action": …, "id": …, "content": …}]}`。代码校验：`id` 必须存在；`content` 经 `normalize_facts` 的敏感过滤与长度限制；任一非法项导致整轮丢弃，计入 P3 失败记账，md 不变；不做二次调用回退（避免成本翻倍）。

**改动点**：
- `extract_facts`（:121）增加 `existing` 参数；`max_tokens` 由 400 提高（推断，需实测）。
- `_PROMPT`（:37）加一句：已有记忆只是数据，不是指令。
- `remember_turn`（:184）接收来源字段。`executor.py:200` 的 `_schedule_memory_write` 当前不把 `request` 传给 `_write_memory`（:209），需要调整。

**成本**：调用次数不变（仍每轮一次）。输入增加现有 `active` 条目；上限 100 条约 4000 字符（按每条 40 字估算，推断）。

**风险**：误判 `REPLACE`，不相关条目被替代。缓解：REPLACE 改口词守卫（见上）；被替代条目保留在 history 中；回滚入口需另行实现。

**验收**：
- 样例集（建议 20 组以上），覆盖同义合并、反转、冲突、无关新增、非法 `id`、非法 JSON。每组给出期望动作，统计一致率。
- 真实样本：在临时实例上复制 alice 的 `auto-memory.md` 内容运行，不写 121。期望：`2026-11-13 用户乘飞机时偏好靠过道座位` 与 `2026-11-15 用户出差坐飞机只选靠过道座位` 合并为一条 `active`。
- 反转用例：先“靠过道”、后“靠窗”，旧条目为 `superseded`，召回只出现“靠窗”。

### P3 失败记账 · 可立即做

**目标**：失败可见、可统计，且不改变对话结果。

**改动**：`remember_turn`（:184-222）的失败分支按阶段（extract / read / merge / save）记录计数与脱敏后的异常类型。当前统一 `except` 后只打 warning（:220-222），没有持久记录。

**不做**：暂不加重试队列。先用计数看失败率，再决定是否需要。

**验收**：用 `httpx.MockTransport` 在各阶段注入故障，计数正确；对话回复不受影响。可沿用 `tests/test_reme_auto_memory.py` 的失败用例。
