ActiveAgent 三重校验门禁与惰性淘汰机制

解析 get_active_agent 为什么要在读取活跃票据时进行三道条件校验，以及为什么任何一条不满足就要立即执行物理清理。

📍 src/gogo_agent/chat/continuation.py: Lines 114–120 def get_active_agent(self, request: RequestContext) -> str | None 
if (
    record.agent_name not in self.available_agents              # ① 门禁一：身份白名单校验（防止僵尸/未注册 Agent）
    or record.expires_at <= datetime.now(timezone.utc)           # ② 门禁二：时效性 TTL 校验（MySQL 缺乏原生到期淘汰）
    or self._session_store.load_agent_state(key, agent_name=record.agent_name) is None  # ③ 门禁三：记忆状态完整性校验（防止孤儿票据）
):
    self._session_store.delete_active_agent(key)                 # 💥 触发动作：惰性驱逐（Lazy Eviction）物理删除 MySQL 记录
    return None                                                  # 🔄 安全降级：平滑回退到意图识别与 Master 流水线
01
门禁一 · 合法性

白名单/注册校验

record.agent_name not in self.available_agents

解决痛点：系统迭代时下线了旧 Agent，或者数据库残留了历史实验性 Agent 的脏名称。

为何关键：如果直接唤醒一个代码里已经不存在或未注册的 Agent，后续会触发 KeyError 或对象未初始化崩溃。

当前白名单：frozenset({"InfoAgent"})。只有显式注册的合法子 Agent 才有资格被快速续跑唤醒。
02
门禁二 · 时效性

逻辑 TTL 过期校验

record.expires_at <= datetime.now(timezone.utc)

解决痛点：活跃票据存储在 MySQL 中，MySQL 原生不像 Redis 那样具备 Key 自动到期消失（Expire）的能力。

为何关键：如果用户昨天问完天气，今天发送“好的”，若无 TTL 校验，系统会误把新话题强塞给昨天的子 Agent，造成严重答非所问。

有效期窗口：默认 30 分钟。超过 30 分钟未交互，该票据自动失效，必须重新走全量意图规划。
03
门禁三 · 完整性

孤儿票据/记忆探测

load_agent_state(key, agent_name) is None

解决痛点：“票据（路标）”与“记忆（AgentState）”是两张独立的记录。路标在，不代表记忆还在。

为何关键：如果内存/持久化中的上下文被单方面清除，只剩下一张空头门票，贸然直连会直接抛出 ValueError("活跃 Agent 状态已丢失") 致命异常。

前置防御：必须保证“门票有效”且“上下文记忆完好”，才允许放行走直连通路。

📥
用户发送新消息 (Turn N)
系统根据 RequestContext 生成 Session Key（如 5:u_001:session_123:router），尝试从 MySQL 读取 ActiveAgentRecord。
🔍
三重门禁原子化检验
依次核对：① 名字是否在 available_agents？ 且 ② 当前 UTC 时间是否在 expires_at 之前？ 且 ③ load_agent_state 是否真实存在？
❌
任一条件失败：触发 delete_active_agent(key) 并返回 None
1. 惰性清除（Lazy Eviction）：在读操作时顺手执行 DELETE FROM agentscope_session WHERE state_key='active_agent'，清理无效数据，避免下次请求继续读脏数据。
2. 安全降级（Safe Fallback）：返回 None 后，主路由放弃快速通道，平滑降级走完整意图流水线（Qdrant 检索 → LLM 分类 → MasterAgent 编排）。
✅
全部条件通过：返回 record.agent_name
进入快速续跑通道（Fast Path）：跳过 Qdrant 和意图分类模型，直接唤醒上次的子 Agent（耗时从 5~8s 锐减至 1~2s，节省全部前置 Token）。
💡 为什么这叫“惰性驱逐（Lazy Eviction）”？
MySQL 本身不会在 30 分钟整的那一秒钟自动执行 Delete。系统采取了最经济的策略：“查到你的时候，发现你过期/损坏了，就顺手把你给删了”。既不需要额外的定时扫描后台任务（Cron Job），又保证了脏数据不会长期占用或干扰系统。
