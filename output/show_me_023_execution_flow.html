从 HTTP 请求到 MasterModel._call_api

一条贯穿 FastAPI、IoC 控制反转、工厂方法覆写与 AgentScope 多态推理的完整调用链路，用 Java 经典工程化思维轻松看透！

🧭 1. 十步调用全景：HTTP 如何一路打穿到 _call_api
1

TestClient 模拟发出 HTTP 请求 HTTP 入口

测试启动 In-Process 测试客户端，向 /api/chat/{session_id} 发起 POST，带上 Alice 用户的 JWT 认证头。

response = TestClient(app).post(f"/api/chat/{session_id}", headers={...}, json={"message": "请介绍一处景点"})
2

FastAPI 依赖解析：命中 dependency_overrides IoC 控制反转

路由方法 send_chat_message 声明了 Depends(get_chat_executor)。FastAPI 检查发现容器中注入了测试指定的覆盖项，取出已准备好的测试 executor 实例。

app.dependency_overrides[get_chat_executor] = lambda: executor
3

控制器委托：调用 executor.execute_turn() 业务服务

Controller 校验用户身份后，将调用转发给执行器。执行器负责保存用户消息、调度意图流水线并准备 Agent 环境。

reply_text, msg_id = await executor.execute_turn(session_id=sessionId, user_id=current_user.user_id, message=req.message)
4

装配智能体：执行 _build_agent() 组装编排

意图识别命中 GENERAL_INFO，执行器决定为主 Agent 挂载只读的 info_agent 工具，并开始为其构建模型驱动。

agent = self._build_agent(state=agent_state, prepared=prepared, request=request, tool_calls=tool_calls)
5

【核心拐点】调用动态覆写的 _build_model 工厂 工厂方法覆盖

_build_agent 内部调用 self._build_model()。但在脚本中，该方法被猴子补丁（动态绑定）替换为了本地闭包 build_model！

executor._build_model = build_model # 第一次被调用时 created=1，返回 master_model
6

组装 AgentScope Agent：注入 master_model 面向接口多态

AgentScope 的 Agent 对象接收 master_model 作为底层推理驱动。Agent 只依赖其抽象契约，完全不知道它是真实的 DeepSeek 还是 Mock 替身。

return Agent(name="GoGo", model=master_model, toolkit=toolkit, state=state)
7

启动推理：await agent.reply(...) ReAct 运行

执行器将用户消息封装为 UserMsg 喂给 Agent。AgentScope 启动 ReAct（思考-行动-观察）决策循环。

reply_msg = await agent.reply(UserMsg(name="user", content=prepared.effective_question.question))
8

AgentScope 框架层调用 model(...) 模板方法模式

AgentScope 框架基类 ChatModelBase 定义了通用的重试、拦截与流式适配骨架，内部调用钩子方法 _call_api。

# AgentScope 内部源码： response = await self.model(messages=prompt, tools=tools_schemas)
9

【目的地】执行 MasterModel._call_api 目标命中 🎯

由于 Java 式的多态机制，执行流精确落入我们在脚本中编写的 MasterModel._call_api，输出控制台日志并生成 ToolCallBlock！

async def _call_api(self, model_name, messages, tools=None, ...): print(f" 主 Agent 第 {self.call_count} 次模型调用，可见工具：{names}")
☕ 2. 从 Java 工程化角度怎么理解？（概念一一映射）

很多习惯 Spring Boot / Java 企业级开发的工程师刚看这段代码会好奇：“为什么没有配置 Spring 上下文就能偷天换日？”——其实两者底层的软件工程设计模式完全是孪生兄弟！

1. HTTP 容器内驱动 Spring: MockMvc

3. 模型构造控制 Spring: 工厂方法覆写 
// Java: 重写工厂方法或注入 MockFactory
public class TestExecutor extends ChatAgentExecutor {
    @Override
    protected ChatModel buildModel() {
        return this.created++ == 0 ? masterModel : infoModel;
    }
}
Python: 实例方法动态覆盖 
# Python: 动态替换实例方法 (Duck Typing / Monkey Patch)
def build_model(stream=False):
    created += 1
    return master_model if created == 1 else info_model

executor._build_model = build_model
4. 模型执行钩子 GoF: 模板方法模式 
// Java: 抽象基类定义执行骨架，子类实现具体网络钩子
public abstract class BaseChatModel {
    public final ChatResponse call(...) {
        // 通用重试、日志、校验
        return callApi(...); // 抽象钩子
    }
    protected abstract ChatResponse callApi(...);
}
AgentScope: _call_api 多态扩展 
class MasterModel(_FallbackMockModel):
    # AgentScope 内部会在 model.call() 时回调 _call_api
    async def _call_api(self, model_name, messages, ...):
        return ChatResponse(...)
💎 3. 为什么这样设计？架构师的思考维度

1. 零网络依赖与极速运行

通过替换 _build_model，整个端到端测试不需要连接真实 DeepSeek 网关，耗时从几秒缩短到 50ms，且完全不消耗 Token 费用。

2. 确定性测试 (Deterministic)

真实大模型具有不可预测的温度概率与幻觉，MockModel 能够精准控制第一轮返回 ToolCallBlock、第二轮返回文本汇总，实现 100% 稳定的自动化回归。

3. 契约真实性 (Real In-Process Wire)

虽然模型是 Mock 的，但 HTTP 序列化/反序列化、鉴权校验、意图流水线规则判断、AgentScope 的 Toolkit 工具调度、ChatHistory 数据库保存**全都是 100% 真实生产代码**。

4. 深度安全防御演练

在不修改核心业务代码的情况下，可以轻松向 MasterModel 注入 write_order（越权工具），从而证明系统的白名单机制能在模型产生幻觉时精准阻断。
